## 第 2 章 選定理由① — ウェルフォート業務への深い理解

### 2.1 既存実装実績 (Wellfort HP / EC リニューアル)

UNFIX 社は **2026 年 4 月に当社の HP / EC サイトのフルリニューアル** を完了・納品済であり、当社サービスの業務全体に対する深い理解を有している。具体的には以下を実装済である。

| 領域 | UNFIX 社による実装実績 |
|---|---|
| 顧客マスタ | 氏名・性別・生年月日・連絡先・住所・配送先のデータモデル設計および登録 UI |
| 商品マスタ | 検査キット (人間ドック / 血液 / 遺伝子 / がんリスク / AI 疾病予測) の商品体系 |
| 受注・配送管理 | 注文 → 出荷 → 配送 → 受領 → 検査会社送付 → 結果受信の全フロー DB 設計 |
| 検査キット管理 | 4 検査会社 (リージャー / PREVENT / Genoplan / LAiF) との API 連携設計 |
| 認証基盤 | Google One Tap 認証の HP マイページ統合 |

### 2.2 業務理解が本補助事業に不可欠である理由

本補助事業の核心である **Supabase 2 スキーマ分割設計** (customer schema / diagnosis schema) は、既存の Wellfort HP / EC 側の顧客マスタ・商品マスタとの **整合性ゼロダウンタイム移行** が必須要件である。

この整合性確保には、既存 DB スキーマを設計・運用しているベンダーが本事業も担当することが最も合理的である。他社に切替えた場合、以下のリスクが生じる:

| リスク | 影響度 |
|---|---|
| 顧客 ID マッピング不整合による顧客データ消失 | **致命的** (個人情報インシデント) |
| 商品マスタ齟齬による検査キット出荷誤り | **重大** (顧客満足度低下) |
| マイページ認証基盤 (Google One Tap) の二重実装 | **重大** (UX 劣化・運用コスト増) |
| 検査会社別 API 連携の重複開発 | **重大** (工数 +30〜50% 増) |

UNFIX 社による単独委託により、これらのリスクは **構造的に排除される**。

## 第 3 章 選定理由② — AWS システム全体の設計・構築・運営能力

### 3.1 委託範囲: AWS インフラ全体 (Elith AI を含む)

本補助事業のシステムは、**当社 (Wellfort) の AWS アカウント** 上で稼働する。
このアカウント内には Web アプリケーション (UNFIX 担当) と AI 推論システム (Elith 担当) の **両方** が同居するが、**インフラ全体の設計・構築・運営は UNFIX 社が一元的に担当** する。

具体的なインフラ責任範囲は以下のとおり:

| 領域 | UNFIX 社の責任内容 |
|---|---|
| AWS アカウント設計 | ① IAM 設計 (Wellfort / UNFIX / Elith / 外部監査の 4 ロール分離)<br>② VPC・サブネット・セキュリティグループ設計<br>③ 3 省 2 ガイドライン準拠の暗号化・監査ログ設計 |
| Web アプリ層 | Vercel (フロント) + Supabase (BE) のセットアップ・本番運用 |
| AI 連携層 | ① S3 (`raw/` `analysis/` `logs/` の 3 層構成) の構築<br>② SQS による非同期バッチキュー設計<br>③ HMAC 署名による Wellfort ↔ Elith I/F セキュリティ<br>④ Elith 側コンテナとの権限分離設計 |
| Elith AI コンテナ稼働基盤 | ① ECS / Fargate 等のコンテナ実行環境構築<br>② Elith が提供する Docker イメージのデプロイ運用<br>③ コンテナログ・メトリック収集 (CloudWatch) |
| 監視・運用 | ① CloudWatch アラート設定<br>② インシデント発生時の一次切り分け窓口<br>③ 10 年間の監査ログ保管 |
| バックアップ・DR | ① RDS スナップショット・S3 バージョニング<br>② 災害復旧手順書の整備 |

**重要な点として、Elith 社は AI 推論ロジック (RAG / LLM / 出力整形) の中身のみを責任とし、AI コンテナを動かす AWS インフラ自体は UNFIX 社が責任を持つ。** これにより、Wellfort は AI ロジックの専門性 (Elith) とインフラ運営の責任 (UNFIX) を明確に分離しつつ、運営窓口は UNFIX 社 1 社で完結する体制を取ることができる。

### 3.2 AWS インフラ運営能力が補助事業全体の成否を決定づける理由

本補助事業の AWS インフラは **3 省 2 ガイドライン準拠** が必須であり、以下の高度な技術要件を満たす必要がある:

- 全通信経路の SSL / TLS 暗号化
- PII (個人特定情報) と診断データの **論理的・物理的分離**
- 監査ログの **10 年間保存** (改竄不可)
- 暗号化キー管理 (AWS KMS による顧客管理キー)
- IAM 最小権限原則
- 災害復旧 (DR) 設計

UNFIX 社は AWS 環境上での金融・医療・教育系プロダクト開発実績を持ち、上記要件をすべて満たす設計能力を有することを既に当社の HP / EC リニューアル案件で実証している。他社委託 (特に複数社に分割した場合) では、**責任分界点での認証・暗号化の整合性確保が困難** となり、3 省 2 ガイドライン準拠の達成リスクが大幅に増大する。

## 第 4 章 選定理由③ — AI 駆動開発実績と既存 AI プラットフォームの流用

### 4.1 AI 駆動開発による開発期間の劇的圧縮

本補助事業は **2026 年 9 月 1 日の公式ローンチ** を目標としており、開発実施期間は **2.5 ヶ月 (10 週間)** のタイトなスケジュールである。従来開発手法では同規模システムに 11 ヶ月以上を要するところ、UNFIX 社は **AI 駆動開発手法を確立** しており、以下を全面活用することで開発生産性を 3〜5 倍に向上させている:

| ツール | 用途 |
|---|---|
| Claude Code Max | AI コーディングエージェント (CLI) — 設計判断 + 大規模実装 |
| Cursor Pro | AI 統合開発環境 — リアルタイム補完 + リファクタリング |
| GitHub Copilot Business | コード補完 + プルリクエストレビュー支援 |

この生産性向上により、補助金事業期間の **大半を運用検証 + 機能改善 + 売上実績計上に活用可能** となり、補助金交付の趣旨である「事業化と売上達成」に直結する。

### 4.2 UNFIX 社の既存 AI プラットフォーム流用

UNFIX 社は本補助事業に先行して、**自社負担で AI プラットフォームをパイロット実装** している (補助金対象外)。具体的な成果物は以下のとおり:

- **検査表 AI スキャン PoC** (Gemini 2.5 Flash Vision + 構造化 Markdown 出力)
- **AI 問診 PoC** (5 セクション / 17 質問 / 音声 Live API + テキスト + 選択肢)
- **設計ドキュメント 12 本** (システム設計 / DB 設計 / Elith 連携 / 検査キット進捗 / 認証 等)

#### 4.2.1 パイロット版を短期・高品質で提示できた根拠 — UNFIX 社内に蓄積された流用可能なプラットフォーム技術

本パイロット版を **わずか数週間で本番品質の動作デモにまで仕上げられた背景には、UNFIX 社内に他案件で蓄積された「直接流用可能なプラットフォーム技術資産」が既に存在していた** という決定的な事実がある。一般的にこのレベルのデモを「ゼロから」構築すれば 3〜6 ヶ月の助走期間が必要となるが、UNFIX 社は以下の社内資産を即時に組み合わせることで、**短期間に高クオリティのパイロット成果物を当社にご提示することができた**:

| カテゴリ | 流用された UNFIX 社内資産 | パイロットへの貢献 |
|---|---|---|
| フロントエンド基盤 | Astro + Tailwind + Vercel 配信パターンの内製テンプレート (SSR・PWA・モバイル最適化済) | ダッシュボード / 結果表示 / AI 問診の UI を最短時間で構築 |

| 音声インタラクション | Web Speech API (STT / TTS) と Gemini Live API のハイブリッド音声制御パターン | AI 問診の音声 UX を短期間で実装 |

| AI 駆動開発環境 | Claude Code Max + Cursor + Copilot を中心とした内製開発ワークフロー | 単純実装の 80% を AI が担い、人間は設計判断に集中 |

これらは **特定の顧客・案件専用に作られたものではなく、UNFIX 社が複数の顧客・プロジェクトを通じて中長期的に磨き込んできた汎用プラットフォーム技術** であり、本補助事業に対して即時・無償で流用可能な「立ち上がり済」の資産である。

この事実が意味するところは以下のとおり:

1. **「短期に高品質のパイロットを提示できた」事実そのものが、UNFIX 社の保有技術が本事業の要求水準を既に超えていることの実証** である
2. パイロット成果物は単発の試作ではなく、**社内の継続改善された基盤の上に乗ったもの** であるため、本補助事業の本格化フェーズにおいても **後戻りや作り直しが発生しない**
3. 他社に切替えた場合、これらの基盤資産は **譲渡・移管不可** (UNFIX 社の知的財産) であるため、**ゼロからの再構築が必要** となり、本補助事業期間内の完了は事実上不可能

#### 4.2.2 委託先切替が成立しない構造的理由

本補助事業ではこれらの実装基盤を流用するため、**他社委託の場合に必要となる「設計コンセプト引き継ぎ」「ノウハウ習得」「プラットフォーム再構築」工程** が不要となる。他社で同等品質に到達するには別途 3〜6 ヶ月の助走期間が必要となり、本補助事業期間中の完了は事実上不可能である。

このため、**「複数社相見積もり」というプロセスは、本事業においては実質的な意味を持たない**。仮に相見積もりを取ったとしても、(a) 同等の社内プラットフォーム資産を保有しない他社は本期間内に納品不可能であるため見積を辞退するか、(b) ゼロからの構築を前提とした非現実的な工数・金額の見積を提示することとなり、いずれにせよ価格比較・選定の合理的判断は成立しない。

## 第 5 章 選定理由④ — ネイティブ・マルチモーダル AI による次世代スキャン技術 (パイロット V1 実証済)

### 5.1 AI スキャン機能が本事業の生命線である理由

本補助事業の革新性の中核は、**ユーザー (会員) が手元の紙の検査票をスマホで撮影するだけで、検査値が自動で構造化・取込される** ことにある。これは従来「スタッフが 1 件 15〜30 分かけて手動転記」していた業務を **数十秒で自動化** する技術であり、補助事業の費用対効果のほぼすべてを決定づけるコア機能である。

しかし AI スキャンは技術難易度が高く、以下の課題を同時に解決できる開発ベンダーは国内で極めて限定される:

| 技術課題 | 必要となる能力 |
|---|---|
| 紙の検査票が **手書き混じり** で書式が検査会社ごとにバラバラ | マルチモーダル LLM のプロンプト設計力 |
| 1 枚の用紙に **複数のテーブル領域** が並ぶ (左右 2 段組等) | 領域検出 (Region Segmentation) ロジック |
| 数値・単位・基準値・H/L 判定の **列対応** を正確に把握 | 構造化 Markdown 抽出設計 |
| 検査会社の **手書き赤線・蛍光ペン強調** を「重要項目」として認識 | 視覚的注釈の意味抽出 |
| **誤読のリスクをユーザーに開示** し、人間による最終確認を促す UI | Human-in-the-Loop UX 設計 |

UNFIX 社は **これらすべてをパイロット V1 段階で実装・実証済** であり、本補助事業期間内での本格化が現実的に可能である唯一のベンダーである。

### 5.2 「従来 OCR」と「ネイティブ・マルチモーダル AI スキャン」の本質的相違

UNFIX 社のパイロット V1 が実装している AI スキャンは、**従来の OCR (光学文字認識) スキャンとは技術原理が根本的に異なる**。本補助事業のスキャン技術が「次世代」である核心は、最新の大規模マルチモーダル AI モデル (本パイロットでは Google Gemini 2.5 Flash) の **ネイティブ・マルチモーダル機能** を活用し、AI が画像内の文字を「読む」のではなく **文字・表・記号・手書き注釈の意味を「理解」して構造化する** 点にある。

#### 5.2.1 アプローチの比較

| 観点 | 従来 OCR スキャン | **ネイティブ・マルチモーダル AI スキャン (本パイロット)** |
|---|---|---|
| 技術原理 | 画素から個別文字を 1 文字ずつ識別 → 後段で別途レイアウト解析 | 画像と言語理解を**同一の AI モデルが同時に処理** (End-to-End マルチモーダル) |
| フォーマット対応 | **事前にテンプレートを登録**した検査票のみ対応<br>(検査会社・帳票ごとに学習・調整が必要) | **テンプレート登録一切不要**。人間ドック・健康診断・血液検査・任意の検査会社の任意レイアウトを **その場で文脈理解** |
| 表構造の認識 | 罫線検出 + ルールベースのセル分割<br>(罫線が薄い・斜め・歪んだ撮影では崩れる) | 「これは検査項目の表である」と AI が**意味として認識**し、罫線が無くてもセルを正しく対応付け |
| 列の対応 | 座標ベースで「○番目の列」を機械的に割当<br>(列の幅やズレに脆い) | 「読取値」「単位」「下限値」「上限値」を **列ヘッダの意味**から判定。並び順が違っても正しく対応 |
| 手書き文字 | 認識精度が著しく低下<br>(辞書登録の手書きパターンに限定) | **前後の文脈** (隣のセル / 同じ行の項目名 / 一般的な検査基準値) を AI が参照して推論。「6.1」が読みづらくても、隣に「総たん白 / 単位 g/dl / 基準 6.6〜8.1」とあれば「6.1」と確信を持って判定 |
| 赤線・蛍光ペン強調 | 認識不可 (色情報を捨てるか、別途ルール実装が必要) | **AI が「赤ペンで強調 = 注目すべき箇所」と意味理解** し、抽出結果に「強調」タグを自動付与 |
| 異常値判定 (H/L) | 文字として「H」「L」を拾う程度<br>(判定根拠の説明不可) | 値と基準値を **AI が比較理解** し、自ら「H 判定」を再現できる<br>(誤読の検出にも寄与) |
| 誤読リスクの自己申告 | 不可能 (OCR エンジンは「自信」のスコアしか出さない) | **「この行は信頼度が低い」「ここはユーザー確認推奨」を AI が自然言語で表明** できる (本パイロットでは 58 件中 18 件を要確認に列挙) |
| 多言語・記号 | 言語別エンジンの切替が必要 | 日本語・英語・略号 (AST / GPT / γ-GTP 等)・単位 (mmol/l, µg/ml 等) を**同一モデルが同時処理** |
| 新フォーマット対応コスト | 1 フォーマット追加 = 学習・調整工数で数日〜数週 | **コスト ≒ ゼロ** (プロンプトを更新するだけで即対応) |

#### 5.2.2 「AI が理解している」ことの実例

本パイロットの AI スキャンが「文字を読む」のではなく「内容を理解している」ことは、以下のように具体的に観察できる:

- **項目名の異表記を自動同定**: 「総たん白」「総タンパク」「TP」「Total Protein」をすべて同じ検査項目として扱える (OCR では別物として登録が必要)
- **単位の常識補完**: 「AST 26」だけ書かれていても、「血液生化学検査の AST であれば単位は U/L である」と AI が補完
- **基準値の医学的妥当性チェック**: 抽出した値が医学的にあり得ない範囲 (例: 血糖値 5000 mg/dL) であれば「読み取りエラーの可能性」として「要確認」に分類
- **手書き赤線の対象セル特定**: 蛍光ペンや赤鉛筆の引き方が雑でも、「隣接行のどの値を強調しているか」を文脈から推定

#### 5.2.3 認識力・理解力における圧倒的優位

総じて本パイロットの AI スキャンは、**従来 OCR と比較して以下の点で次元の異なる優位性** を有する:

| 項目 | 従来 OCR の到達点 | 本 AI スキャンの到達点 |
|---|---|---|
| 認識精度 (印字) | 95〜98% (整った帳票) | **≒ 100%** (同条件) |
| 認識精度 (手書き) | 60〜80% (辞書登録パターンのみ) | **90〜98%** (文脈推論あり) |
| 新フォーマット立ち上げ | 数日〜数週 (テンプレ作成必要) | **即日** (プロンプト調整のみ) |
| レイアウト崩れ耐性 | 弱い (罫線・列ズレで崩壊) | **強い** (意味理解で吸収) |
| 強調マーカーの解釈 | 不可 | **可能** (タグ自動付与) |
| 誤読の自己申告 | 不可 | **可能** (要確認件数として列挙) |

この技術的優位こそが、**本補助事業が「単なる OCR 導入」ではなく「次世代健康データ取込基盤の構築」と評価されるべき所以** である。UNFIX 社はこのネイティブ・マルチモーダル AI スキャンを**既にパイロット段階で本番品質に到達させている**唯一の委託先であり、本補助事業の革新性を期間内に達成するには UNFIX 社への単独委託が技術的に必須である。

## 第 6 章 選定理由⑤ — 単一委託による責任分界の最適化

### 6.1 v1.0 (2 社分散) から v2.0 (1 社統合) への変更経緯

本補助事業の初版 (補助事業要件定義書 v1.0) では、Web アプリ実装を H&K 社に、結合テスト・UAT を別途分散委託する想定であったが、検討の結果 v2.0 にて **UNFIX 社への一本化** に変更した。理由は以下のとおり。

| 観点 | 分散委託 (v1.0) のリスク | 単一委託 (v2.0) のメリット |
|---|---|---|
| 責任分界 | 実装ベンダーとテストベンダーの境界で「品質責任の押し付け合い」が発生する懸念 | 実装〜結合テスト〜UAT を一気通貫で UNFIX が責任を負う |
| コミュニケーションコスト | 3 社 (Wellfort + 実装 + テスト) 間の調整工数 | 2 社 (Wellfort + UNFIX) で完結 |
| スケジュール | テスト工程で手戻りが発生した場合の往復工数 | 同一チーム内での即時修正が可能 |
| AI 駆動開発との親和性 | AI で生成したコードのテストを別社が担当することによる学習曲線 | AI 駆動開発の全工程を同一チームが担当 |

### 6.2 切替リスクへの対処

結合テスト・UAT を UNFIX 社内製化することによる「自社テストの客観性低下」リスクに対しては、以下の二重チェック体制を確立する:

1. UNFIX 社内に **QA エンジニア兼任 1 名を専任配置** し、開発エンジニアと独立した検証ラインを構築
2. **セキュリティ監査は外部専門家** に委託し、UNFIX 自社テストとは独立した監査ラインを維持
3. **医療内容監修は医療顧問 (外部)** に委託し、生成 AI 出力の妥当性を独立してチェック

これにより、単一委託のメリット (責任明確化・コミュニケーション最適化) を享受しつつ、客観性・独立性のリスクは適切に統制される。
