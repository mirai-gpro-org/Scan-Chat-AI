# 相談: 健診票 画像→構造化JSON スキャンの「run間 非決定性」を下げたい

健康診断結果票（紙）を **Gemini マルチモーダルで OCR＋構造化** し、外部連携用 JSON を生成するパイプラインを運用しています。
**数値項目の精度は高い**のですが、**同一画像・同一プロンプトでも run ごとに一部の定性/境界項目の読み取りが揺れる（非決定）**のが最後の課題です。実務的な下げ方について、忌憚のないフィードバックと改善案をください。

---

## 1. システム構成（前提）

- **モデル**: `gemini-3.1-flash-lite`（軽量・安定重視。上位の flash 系は混雑時 503 が多くバッチ全滅の実績があり据え置き）。ネイティブ・マルチモーダル、REST 呼び出し。
- **実行環境**: Vercel Serverless（関数タイムアウト ~60s）。**1 画像 = 1 リクエスト**でクライアントが順に呼ぶ（大判の検査表を1発で投げるとタイムアウト/精度劣化のため）。
- **入力**: 検診票 5 枚（身体計測・血圧・視力/眼底/眼圧/聴力、血液/脂質/肝/腎、所見、主要検査、基本情報）。
- **出力**: ページごとに **10 列の GFM テーブル**（Markdown）で返させ、後段のプログラムで決定論的にパースして JSON 化。
  - 列: `No | 検査項目 | 検査項目詳細 | 読み取った値 | 推論値 | 単位 | 下限値 | 上限値 | 判定 | 備考`
- **時系列の扱い（仕様）**: 検査票には「今回 / 前回 / 前々回」の複数回列が横に並ぶ。**採用するのは「今回」列のみ**。今回が空欄ならその項目は空（前回値を繰り上げない）。
- **後段の正規化はプログラムに集約**（LLM に整形・判定はさせない）:
  - `↑↓` → 判定フラグ(H/L)、数値化、空行（未実施）除外、総合判定(A/B/C)欄 除外 など。
  - 生成 JSON の各測定値は `{name, value, value_num, unit, ref_low, ref_high, flag}`。

## 2. 品質の測り方（決定論ゴールデン照合）

LLM による「画像↔JSON 照合」も作りましたが、**採点側の LLM も同じ列帰属の弱点を持ち非決定**でノイズが乗るため、
**人手で確定した「今回」列の正解（ゴールデン）と、生成JSON を項目単位で突き合わせる決定論チェッカ**を主指標にしています。
- 指標: 一致率 / Missing（今回値の取りこぼし）/ Column-Shift（過去列の値を今回に採用）/ Wrong-Value / False-Value（今回=空なのに値あり）。
- 名称の表記ゆれは**照合器側で正規化**して吸収（空白除去＋末尾「数/量/値」除去＋同義語エイリアス）。

## 3. 実測データ（同一 5 枚・同一プロンプトで 2 回 RUN）

| 観点 | RUN 1 | RUN 2 |
|---|---|---|
| **numeric 29 項目**（身長/体重/BMI/血圧/血算/脂質/肝/腎/尿酸/眼圧 …） | **全一致** | **全一致** |
| 項目名の表記 | `最高血圧`, `白血球数`, `裸眼視力右` | `最大血圧`, `白血球`, `裸眼右`（**同じ値だが名称が変動**） |
| 免疫便潜血反応（今回=陰性 `(-)`） | `(-)` を **上限値列に誤配置**し読取値=空 → 納品脱落（取りこぼし） | **正しく読取値列に `(-)`**（正） |
| K-W分類 右/左（今回=`0`） | **`0` を正しく読取** | **空欄 `-` で返す** → 脱落（取りこぼし） |

**要点**:
- **数値の読取そのものは極めて安定**（29/29 が両 run 一致）。矢印(↑↓)や桁・小数点の誤りも無し。
- 揺れるのは **(a) 項目名の表記** と **(b) 定性/境界項目の「列帰属・空欄判断」**。
  - (a) は後段の名称正規化で解消済み（照合器・納品名とも影響軽微）。
  - (b) が本質的な残課題。**毎回 1〜2 項目だけ、しかも入れ替わりで**発生する。
    - 特に「陰性 `(-)`」が **その項目の“今回結果”なのか、欄外の“基準表記 (-)”なのか**をモデルが取り違え、`上限値`(基準)列へ入れてしまう run がある（尿糖/尿蛋白/尿潜血の `(-)` は安定して読取値列に入るのに、便潜血だけ様式差で揺れる）。
    - K-W 分類（正常=`0`）のように **淡い/小さな数字**が run により空欄化する。

## 4. 制約・これまでの失敗（重要）

- **プロンプトを凝ると回帰する実績**: 「今回列を確実に取らせる」ため列アンカリングを3列スペーサ方式に作り込んだところ、
  狭いマーカ列（↑↓）付近で**1列右シフト**が起き、身体計測・血圧・視力が壊れて全リバート。**単一列＋最小指示が最も安定**という教訓。
- **キーは Vercel 環境変数のみ**（ローカル/クライアント不可）。処理はサーバ側。
- 生成設定: 3.x では `temperature/topP/topK` は既定で**除去**（推奨に従い未指定）。`thinking` は薄め。
- **1 画像 = 1 リクエスト・60s** の制約下。多数決（N 回スキャン）はコスト/レイテンシに直結。

## 5. 聞きたいこと（フィードバック＆改善案）

1. **run間 非決定性を下げる実務策**: 同一画像・同一プロンプトでの出力揺れ（特に定性の列帰属・空欄項目の読取）を下げるには？
   - 3.x で除去している **`temperature=0` 等を敢えて戻す**べきか？ `thinkingLevel`（思考量）を上げる効果は？ **seed 固定**は Gemini で有効・実用的か？
2. **「陰性 (-)」の列取り違え**（結果の (-) が基準表記の (-) と混同され `上限値`列へ入る）への、**最小プロンプト or プロンプト以外**での堅い対策は？（3列アンカリングで懲りているので、大改修は避けたい）
3. **多数決 / セルフコンシステンシ**: numeric 精度を保ちつつ、定性/境界だけ **N 回読んで安定値を採用**する設計は現実的か？ 1画像1リクエスト・60s の制約下での妥当なやり方（例: 揺れる項目だけ再問い合わせ、票の取り方）。
4. **項目名の表記ゆれ**: モデル側で名称を固定させる（列見出しを厳密指定 等）べきか、**後段正規化に任せる**（当方の現方針）べきか。ベストプラクティスは？
5. **アプローチ全体の妥当性**: 「10列 Markdown 表で返させ → 決定論パース＆正規化 → 人手ゴールデンと決定論照合」という設計そのものの評価・改善点。ネイティブ構造化出力（responseSchema/JSON mode）へ寄せるべき局面はあるか？（表のレイアウト依存の列帰属問題に効くか？）

## 6. 参考: 現状の到達点（誇張なし）

- 数値項目は決定論照合で **両 run 全一致**。名称ゆれは吸収済み。
- 残るのは **定性/境界の 1〜2 項目が run 毎に入れ替わりで落ちる**点のみ。
- ここを**過剰なプログラム/プロンプト制御に頼らず**安定させたい、というのが相談の核心です。
