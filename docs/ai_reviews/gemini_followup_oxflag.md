## 我々の懸念（＝全行スキーマ/プロンプト変更のリスク）

提案1は Markdown 列を1本増やす＝**全行・全項目にかかるプロンプト/スキーマ変更**です。本プロジェクトには、これに類する変更で**回帰した実績が2件**あります。

1. **responseSchema(JSON)化の失敗**：まさに「value と ref を別フィールドに固定して Semantic Tie を構造的に断つ」狙いで responseSchema を導入したところ、**逆に未実施項目の value に基準値を流し込む捏造（False-Value）が多発**（実測8件）して不採用になりました。「モデルに考えさせる補助フィールドを増やすほど、別の誤りが出る」挙動です。
2. **別機能でのプロンプト分岐追加による回帰**（AI問診の制御をプログラム側で足した結果、読み上げが途切れる回帰）。

補足：後段パーサは列を**名前で引く**実装（`indexOf(列名)`）なので、列を足しても**パース自体は壊れません**。したがって懸念は**「LLMの振る舞い」側**——**現在 run 間で完全一致している numeric や、他レイアウトの読み取りが、列追加で不安定化しないか**、という一点に集約されます。

もう一つの助言者（ChatGPT）は、この点について明確に「**列アンカーをさらに複雑化してはいけない（別ページが壊れる）**」と述べ、列追加ではなく「プロンプトでのCell Anchor化＋後段の定性辞書サルベージ＋行ROI再読」を推奨しています。

## 最重要の疑問：O/Xゲート自体が False-Value を誘発しないか？

提案1の安全性は「**未実施で空欄の行では、モデルが高確率で `X` を出す**」という前提に依存しています。しかし我々の実データには、この前提を直接脅かすケースがあります。

**具体例（実検体4ページ目・血清検査）**：
- **RPR：基準列 `(-)`、今回列 空欄（未実施）**
- **TP抗体：基準列 `(-)`、今回列 空欄（未実施）**

ここでモデルの根本課題は「基準の `(-)` と結果の `(-)` を判別できない」ことです。だとすると、未実施の RPR 行を見たモデルが「行内に `(-)` が見える」ことに引きずられて **`今回値あり=O` と誤答**し、後段サルベージが基準の `(-)` を value に移送＝**新たな False-Value を生む**、というシナリオが現実的に見えます。

→ **質問A：O/X 判定は、まさにモデルが苦手とする「今回セルの空間特定」を要求します。基準列に `(-)` があり今回が空欄の行で、モデルが安定して `X` を返せる根拠・工夫は？**（False-Value 0 は本システムで最重要指標です）
