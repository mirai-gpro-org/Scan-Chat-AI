# AI問診 — 仕様と設計原則（確定・作業前必読）

この文書は **AI問診（音声/タップのハイブリッド問診）の確定仕様と設計原則**の唯一の正本。
AI問診まわりのコードに触れる前に必ず読むこと。**ここに書かれた確定事項を、推測や場当たり修正で蒸し返さない。**

- 対象コード: `src/scripts/chat/live-controller.ts` / `interview-script.ts` / `live-audio-manager.ts` / `wheel-picker.ts` / `src/pages/chat.astro` / `src/pages/api/live-token.ts`
- 上位の確定事項: `CLAUDE.md` §「AI問診 / Live API 制御 (絶対厳守)」（本書はその詳細版）
- 関連仕様: `docs/funding_application/要件定義書.md` F-3、`docs/interview/20260331_AI参考問診票.png`

## 0. 一行サマリ（これだけは絶対に外さない）

> **問診の「フロー・選択肢・回答データ」はプログラム(InterviewEngine)が制御してよい。
> しかし「音声のターン取り・割り込み・復唱・エコー・“誰がいつ何を喋るか”」は Live API/LLM に完全に委ね、プログラムで制御しない。**

Gemini Live API は VAD・割り込み・ターン取りをモデル(サーバ)側で管理する前提で設計されており、公式もフロー制御を LLM に委ねる方向を推奨。**これと戦うと必ず破綻する**（二重化・読み上げ途切れ・先走りのモグラ叩き）。

---

## 1. アーキテクチャ

- **問診進行**（質問順・分岐・完了・進捗）= クライアントの **`InterviewEngine`**（`interview-script.ts`）が確定的に制御。LLM に問診順を決めさせない → ループ・順序乱れ・選択肢欠落が構造的にゼロ。
- **回答UI**（chip / multi / wheel / matrix / slider / stepper / text）= プログラムが設問種別に応じて描画。タップ回答が一級市民。
- **音声**= **Gemini Live API**（`gemini-3.1-flash-live-preview`）。挨拶・質問読み上げ・回答の復唱・間・割り込みは **LLM が担う**。
- **回答データ** = engine が `AnswerValue` で構造化記録 → Elith `LifestyleQuestionnaireData` として出力。

---

## 2. 責務分界（最重要・これが全て）

| 領域 | 制御主体 | 補足 |
|---|---|---|
| 質問順・分岐・完了（フロー） | **プログラム(engine)** | 確定的。`recordAndAdvance` |
| 選択肢UI・ウィジェット描画 | **プログラム** | `renderChips` 等。設問種別で切替 |
| 回答データの記録・構造化 | **プログラム** | Elith 出力の源泉 |
| タップ回答の受付 | **プログラム** | 音声が無い＝Live API 自発応答なし＝安全 |
| **音声のターン取り / 割り込み / VAD** | **Live API/LLM** | **プログラムで握らない** |
| **音声時の復唱・次質問の“発話”** | **Live API/LLM** | **アプリから発話注入しない**（§4） |
| **エコー/回り込み対策** | **Live API** | マイクゲート等の半二重制御をしない |

> ✅ プログラム制御して良いのは **フロー・選択肢・データ・タップ**。
> ⛔ プログラム制御してはいけないのは **音声の「誰がいつ何を喋るか」**。

## 4. 二重話者問題（現在の既知課題）— 定義・原因・正しい直し方

### 定義
音声で回答すると、**話者が2系統**になり復唱/質問が二重に読み上げられる：
- (a) **Live API の自発応答**（ユーザー音声に反応して復唱）— 会話モデルの本性
- (b) **アプリの注入**（`submitAnswer`→`sendToModel` で「復唱＋次質問」）

### 原因（コードで確定済）
- **`f99f47e`（2026-06-18）**が犯人の起点。設問刷新と同時に **`maybeHandleVoiceAnswer`/`interpretVoiceAnswer` を追加し、音声回答を「アプリ注入経路」に載せた**。
- それ以前は音声回答を **LLM が自分で処理**（自発応答＋`present_question` ツールで engine 同期）＝**1話者**で、二重化は発生していなかった。
- **選択肢UI・engine 駆動・タップ注入は f99f47e 以前から存在**し、問題を起こしていない。＝**engine 駆動が悪いのではなく、「音声のターン/発話をプログラムで握った」ことだけが悪い。**

### 正しい直し方（合意方針＝案1・未実装）
> **フロー・選択肢・データの program 制御は維持**したまま、
> **音声回答時は AI へ発話を注入しない**（＝ Live API の自発応答を唯一の話者にする）。
> engine は transcript から回答を**裏で記録・前進**させるが、**復唱/次質問の `sendToModel` はしない**。
> 次質問を LLM に読ませる必要がある場合は、**Live API 公認の function calling**（LLM が関数を呼び、アプリは次質問を function の戻り値で返す＝**同一ターン・競合発話なし**）で行う。

- ＝ f99f47e が足した「音声→発話注入」**だけ**を外す。変更範囲は最小、確定性は不変。
- ⚠️ 音声UXはモデル・タイミング依存 → **実装は必ず実機確認**とセット。

## 5. 問診内容の仕様

- **5セクション**（`docs/funding_application/要件定義書.md` F-3 / `docs/interview/20260331_AI参考問診票.png`）:
  1. 嗜好品（喫煙・飲酒・カフェイン）
  2. 運動・活動量
  3. 食生活
  4. 睡眠
  5. 心身の健康
- **同意設問・実施検査確認などは問診に含めない**（同意は登録/オンボーディングで取得）。仕様外設問を足さない（実績: `ddeb465` で C-CONSENT 削除）。
- 設問の定義は **`interview-script.ts` に集約**（`live-controller.ts` にハードコードしない）。
- 申込情報から自明な項目（氏名・生年月日・性別・EXAM-TYPE 等）は問診で聞かず、内部取得/供給する。

## 6. Live API 設定・実装上の注意

- モデル: `MODELS.liveChat = gemini-3.1-flash-live-preview`（`src/lib/gemini.ts`）。**preview モデルはサーバ挙動が予告なく変わり得る**（自発応答の強さ等）→ 二重化の“見え方”が時間で変動する要因。挙動が急変したら**モデル版の固定/変更**を第一に検討（これはターン制御ではなく“モデル選択”＝許容）。
- 接続設定（`live-controller.ts` の `ai.live.connect`）: `responseModalities:[AUDIO]` / `speechConfig ja-JP` / `inputAudioTranscription` / `outputAudioTranscription`。
- `realtimeInputConfig.activityHandling`: 現状 `NO_INTERRUPTION`。**turn/VAD 系の設定を安易にいじらない**（挙動が絡む）。変更するなら公式ドキュメント根拠＋実機確認をセットで。
- 重複発話ループ検出（`duplicateAssistantCount`）等の“保険”はあるが、これは最終防波堤であって設計の代替ではない。

## 8. 用語

| 用語 | 定義 |
|---|---|
| 二重話者問題 | 音声回答時に (a)Live API 自発応答 と (b)アプリ注入 の**2系統が喋る**こと。二重化・途切れ・先走りの根 |
| アプリ注入 | `submitAnswer`→`sendToModel` で AI に「復唱＋次質問」を発話させる依頼。**音声では禁止方向**（§4） |
| engine 駆動 | `InterviewEngine` がフロー/選択肢/データを確定制御する方式。**維持する** |
| silent 分岐 | 音声(silent)とタップで注入内容を出し分ける実装。**禁止**（途切れ回帰） |
