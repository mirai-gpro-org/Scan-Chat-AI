## 0. スコープの抜け（今回判明）
- 現状の Webアプリ／Elith 納品フローは **サブスク検査プラン4つ**（`kit_lifecycle_and_handoff_management_spec §1`）を前提に設計。
- しかし EC 商品DBには**サブスク4プラン以外の単品検査商品**が存在し、その購入者への対応が未設計だった。
- → 単品購入者も **マイページ／Webアプリを利用**（データアップロード・問診入力・レポート閲覧）できるようにする必要がある。

## 2. 商品別のフロー（クライアント追加情報 2026-08 を反映）

### ① AI疾病予測報告書（LAiF社・¥55,000）

**フロー（確定）**
1. 購入者が **人間ドックデータを Webアプリのマイページからアップロード**。
2. 購入者が **Webアプリの AI問診に回答**。
3. **上記2つが揃った時点**で、必要データを **CSV へ転記 → Excel ファイルへ変換 → LAiF社へ自動送信**。
4. LAiF社で解析 → **レポートを受信 → Webアプリのマイページにストア**。

- **問診の入手**: WebアプリのAI問診。
- **上り（送信）**: LAiF指定の入力フォーム（Excel）。→ 生成ロジックは `kit_lifecycle_and_handoff_management_spec §4.1.1`／`scripts/build-laif-input.py`（**名前欄＝識別番号を必ずセット**）。
- **下り（受信）**: LAiFからレポート受領 → マイページへストア。
- **Elith 納品（JSON→S3）**: **生じない**（単品購入時）。

### ② AI疾病予防報告書（Elith社・¥7,700）

**フロー（確定）**
1. 購入者が **人間ドック又は健康診断データを Webアプリのマイページからアップロード**。
2. 購入者が **Webアプリの AI問診に回答**。
3. **上記2つが揃った時点**で、データを **OCR → JSON → S3 へストア**。
4. Elith社が**レポートを生成 → PDF化 → マイページへストア**。

- **問診の入手**: WebアプリのAI問診。
- **Elith 納品（JSON→S3）**: **生じる**（①③と異なり、**単品でも Elith 納品が発生**）。
- **成果物**: AI診断結果PDF をマイページへ格納（受取・表示の実装は `lab_data_pipeline_master_spec` ⑥／`elith-report` 経路）。

> **【重要・関連する事業判断】従来の AI疾病予防報告書（Wonderlust社製）は保守契約を解除し停止する（使えなくなる）。**
> 保守管理費用 **15万円／月** の支払いは終了。→ 本商品（Elith社製）が後継となる。

### ③ ジェノプラン遺伝子検査キット（Genoplan社・¥32,780）

**フロー（確定）**
1. 購入者が **検体を送付すると同時に、ジェノプラン社のHPにアクセスしアンケートに回答**（＝**Webアプリの問診は使わない**）。
2. 検査レポート完了後、**RPA でダウンロード**し、**マイページにアップロードして完了**。
3. 別途、購入者は**ジェノプラン社からの案内に対応してレポートを入手可能**（従来通り・並行）。

- **問診の入手**: **検査会社サイトで直接**（Webアプリは関与しない）。
- **下り（受信）**: **RPA による自動ダウンロード** → マイページへアップロード（＝システム/運用側の処理。ユーザー作業ではない）。
- **Elith 納品（JSON→S3）**: **生じない**（単品購入時）。

## 5. 残る要確認事項

1. **①の「CSVへ転記後 Excelファイルへ変換」の実体**: LAiF正式フォームは xlsx（`input_format_new_202312.xlsx`）で、実装（`build-laif-input.py`）は**直接 xlsx を生成**する。「CSV→Excel」は運用上の表現か、中間CSVを実際に作るのか要確認（成果物が正式フォームxlsxであれば実装は現行のままでよい）。
2. **①の「自動送信」の経路**: 既存の合意は **S3（専用バケット）＋専用ポータル＋自動メール通知**（`laif_s3_secure_handoff_spec`）。「自動送信」がメール添付を指すのか、S3/ポータル配置＋通知を指すのか要確認。
3. **②のOCR**: 既存の**AIスキャン機能（HealthCheckupData生成）**を流用する想定でよいか（別OCRではない）。
4. **②のElith納品セットの中身**: 健診/人間ドック＋問診のみでよいか（**ウェルネス年齢(HealthAgeData)の同梱要否**）。→ Elith と要確認。
5. **Wonderlust社製の停止時期と移行**: 停止日、既存利用者への案内、マイページ上の旧レポートの扱い（残す/隠す）。
6. **③のRPA**: `lab_data_reception_overview` の遺伝子=RPA方針と同一のものか（実装・運用主体）。
7. **単品購入者の顧客ID**: `diagnostic_user_id` の採番・マイページ導線はサブスク購入者と同一でよいか。

## 6. 実装への影響（確定後に別途仕様化）

- **購入商品→対応フローの分岐**が必要（サブスク4プラン / 単品①②③）。商品DB（`test_products`）に**単品商品の種別・対応フロー属性**を持たせる想定（`test_kits.kind`＝`data`/`app` と整合）。
- **マイページに「検査結果データのアップロード」機能**が必要（①②）。→ 人間ドック/健診のスキャン経路をユーザー自身が使う導線。
- **「アップロード＋問診の両方が揃った」判定**（トリガー）を実装（①②共通）。→ サブスクの §4.3「揃った時点」判定と同じ機構を流用。
- **書き出し経路をフラグ分岐**: **①③＝Elith納品なし**（アプリ内格納・表示のみ）／**②＝Elith納品あり**。
- **①の上りexport**を単品購入者にも適用（`build-laif-input.py`／本番はNode/TS移植が follow-up）。
- **③はRPA取得→マイページ格納**のみ（問診・Elith連携なし）。
- **レポート格納・表示の共通基盤**: ①LAiFレポート／②ElithPDF／③GenoplanレポートをマイページにストアしてPDF表示できること（`report.astro`／`diagnosis_results` 系の拡張）。
- **Wonderlust版の停止**に伴う、旧レポート表示・導線の撤去。

## 7. 次アクション
1. §5 の残要確認事項をクライアント／Elith／各社へ確認し確定。
2. 確定後、単品対応の**正式仕様**（商品DB属性・フロー分岐・マイページ画面）を `kit_lifecycle_*` と整合させて策定。
3. 単品①②③ごとの E2E（購入→アップロード/問診→各社受渡→結果格納→表示）を `lab_data_pipeline_master_spec` に追補。
4. **Wonderlust停止**の影響範囲（画面・データ・契約）を洗い出し、移行計画を作成。
