## 1. 【最初に読む】ミッションと優先順位

**この順に読むこと。下位の運用ルールを上位の目的より優先すると必ず失敗する
(実際に 3 回失敗した・§6)。**

### 1.1 第 1 層 — 事業のミッション

`docs/funding_application/要件定義書.md:27`

> がん及び生活習慣病を、健康モニタリングにより**早期発見および予防**し、
> 健康寿命を大幅に伸ばし、豊かな人生を実現する。

事業の核心 (同 `:31`) = 「**読ませるレポート**」から「**行動を促すダッシュボード**」へ。
**既存の検査結果報告書はテキスト中心で読解負荷が高く、行動に繋がらない — これが解くべき課題。**

### 1.2 第 2 層 — サービスの 2 本柱

`docs/elith/ai_prevention_report_generation_spec.md` §1.0 (発注者確認 2026-08-28)

```
年 1 回 人間ドック ＋ 年 3 回 血液検査・がんリスク検査   ← 隙間を埋める
              = 年 4 回の検査
                     │
      ┌──────────────┴──────────────┐
 A 検査結果そのもの            B その検査データで AI 診断を回す
 → 初期がんの早期発見           → 疾病予防アドバイス
```

**B の入力は A の検査結果。別系統ではない。**
**「画面設計はこの 2 本柱に従う」** — これが最上位の実装制約。

### 1.3 第 3 層 — 本機能の目的

同 §1.1

> **Elith の出力は文章の羅列で、一般ユーザーが読み通せない。**
> 読みやすく、重要な点が確実に伝わる報告書を、受領データから**アプリが生成する**。

**役割は可読化だけ。** フォーマット変換でも内容の追加でもない。

### 1.4 越えてはならない線

| # | 制約 | 出典 |
|---|---|---|
| 1 | **Elith の出力以上の表記・表現を一切しない** | spec §1.0 (最重要・発注者指示) |
| 2 | アプリが医学的判断を生成しない (ミッション④: 整理して伝える／独自に分析・解釈しない) | spec §1.2 / `CLAUDE.md` |
| 3 | 受領データに無いものは作らない (捏造ゼロ) | spec §6 |
| 4 | 時系列・前回比をアプリで作らない (Elith が織り込み済み・二重の解釈になる) | spec §1.0.2 |
| 5 | 見本 PDF の**内容**を再現しない (様式のお手本であって項目一覧ではない) | spec §1.1 / §1.2 |

**【重要】1 と「可読化」は矛盾しない。** 構造化と要約は別物。
Elith の原文から**逐語で抜き出して構造に置く**のは可 (モックがそれをやっている)。
言い換え・要約・当社の散文の追加は不可。

### 1.5 優先順位 (これを間違えた)

```
事業ミッション (読解負荷を下げ行動に繋げる)
   ↑ 従属
2 本柱 (画面設計はこれに従う)
   ↑ 従属
可読化のルール群 (章立て・材料が無い章は出さない・組版 …)
```

**「材料が無い章は出さない」(§1.0.1・第一級要件) は下位の運用ルール。**
上位の「画面設計は 2 本柱に従う」を潰してはならない。

## 6. 【必読】Claude が犯した 3 つの失敗

**本節の失敗はすべて Claude (Claude Code) が実装時に犯したもの。**
UNFIX・Wellfort・Elith の判断や指示によるものは 1 件も無い。
同じ失敗を繰り返さないために残す。いずれも「**すでに書いてあることを外した**」もの。

### 失敗① 2 本柱を実装に落とさなかった

`axis` を配列を分けるための変数にしか使わず、軸の見出しを一度も描かなかった。
結果、A に材料が無いタイプ 2 (= パイロットの対象) で
「材料が無い章は出さない」が働き、**A 軸の痕跡がゼロ**になって報告書が B から始まっていた。

**原因**: 下位の運用ルールを上位の設計制約より優先した (§1.5)。
**教訓**: **枠 (軸) と中身 (章) を分ける。** 枠は常設、中身だけが条件付き。

### 失敗② 2 本柱が冒頭に来ていなかった

帯を描いた後も並びが `表紙 → 手元に残す → 目次 → 主軸A` で、2 本柱が埋もれていた。
「冒頭に置く」は「描画する」ではなく「**最初に見えている**」こと。

### 失敗③ 設計ポリシーの説明文を紙面に貼った

「年 1 回の人間ドックの隙間を年 3 回の検査で埋め…」
「Welltect は次の 2 つを柱にしています。この報告書も、その順で構成しています」を画面に出した。
これは **Wellfort へ設計意図を説明するための文**であって報告書の中身ではない。
**Claude が書いた散文**を紙面に置いた = §1.0 違反・§1.3.1 の **(c) 内容の創作 = 不可**。

**原因 (①〜③に共通・Claude の作業のしかた)**: 仕様書を `grep` で拾い読みし、
**これから書く実装に合う節だけ**を後付けで読んでいた。
仕様から実装を導かず、実装を決めてから根拠を探していた。
モックも「Wellfort に見せる成果物」として扱い、実装中に一度も開き直さなかった。

**対策**: **仕様書を通読してから着手する。** 節単位の拾い読みをしない。
実装後、モックと画面を並べて突き合わせる。

## 8. 動かし方

```bash
npm run dev                      # http://localhost:4321/report
npm run verify:report-model      # 回帰 55 件
npx astro check                  # 0 errors であること
```

- `/report` … 通常表示 (実データが無ければ 2026-08-26 受領分のサンプル)
- `/report?save=1` … 端末別の保存手順を開く
- `/report?print=1` … 印刷専用ビュー (全展開・UI なし・**`<details>` を使わない**)

**admin の抽出監査** (wellfort-site) で「何を認識し何を落としたか」を確認できる。
`diagnostic_user_id` を空にするとサンプルの監査が出る。**0 件は赤字**。
