# この仕様書の構造 — なぜ普通の仕様書と違うのか

**この機能は 2 回、実装が紙面と違うものになって作り直しになった。**

| 回 | 何が起きたか |
|---|---|
| 1 回目 | 受領本文をそのまま流した。画面 20,297 字 / 受領 20,490 字 = **削減率 1%**。全リバート |
| 2 回目 | ダイジェストを作ったが、**モックと照合しないまま本番へ**。検査値の並びがモックと違っていた |

**2 回とも直接の原因は同じ: 仕様書の散文を読んで実装し、モックを見なかった。**

そこで本書は **紙面のことを一切書かない。**

> ## 【最重要】紙面の正はモックであり、この仕様書ではない
>
> - どのカードが / どの見出しで / どの文を / どの順で 出るか — **すべてモックが持つ**
> - **本書にそれを書き写さない。** 書き写すと「もう一つの正」ができ、実装者がどちらかを選ぶ。**それが 2 回の失敗の正体**
> - 本書が定義するのは **正の所在・素材・変更手順・検証・未裁定** の 5 つだけ

② npm run verify:sheet-contract -- --write   ← 契約 JSON を再生成してコミット
        ↓                                       PR 差分に「紙面がどう変わるか」が文の単位で出る
③ 実装を直す                    ← 契約が通るまで
```

- **契約 JSON を手で書き換えて通すのは禁止。** 必ずモックから再生成する
- 差分が出たら「モックが正」か「モックが古い」かのどちらか。**どちらであれ両方を突き合わせて直す。**
  片方だけ直して通すのは契約の放棄
- 発注者に見せる版は Artifact へ再公開する（type2 = `6eac069b…` / type1 = `d633fc3f…`）

## 5.3 実装の骨格（変えてよいが、層は壊さない）

```
受領JSON  →  report-adapter.ts  →  report-model.ts  →  report.astro
（素材）      （変換規則の唯一の所有者）  （表示モデル）      （画面と ?print=1 が同じレンダラ）
                        ↑
              report-sections.ts + app_config（章の順序・表示可否・見出し・開閉）

- **形式の世代差はアダプタ 1 枚で吸収する。** 画面は表示モデルしか知らない

  `ui.cancer_screening_not_included`。既定は全て空＝コード既定。反映は TTL 45 秒
- **抽出は fail-safe。ただし黙って空にしない。** 拾えなければ何も出さないが、admin の抽出監査に出す
