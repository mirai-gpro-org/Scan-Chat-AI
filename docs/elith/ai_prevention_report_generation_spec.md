## 1. 目的

**Elith の出力は文章の羅列で、一般ユーザーが読み通せない。** 読みやすく、重要な点が確実に伝わる
報告書を、受領データから**アプリが生成する**。

- **入力の正 = JSON** (`report_text.json` / `health_checkup.json`)。
- **見本 PDF (`AI疾病予防レポート` 18p) = 様式のお手本**。埋めるべき項目の一覧ではなく、
  **見せ方**(表紙の作り・章立て・表への落とし込み・視覚的な優先順位) を参考にする。
- **Elith の PDF = 原本**。表示の主役から外し、監査用に保管する。

### 1.1 非目的 (やらないこと)

- 見本 PDF の**内容**を再現すること。見本は別検体 (田宮嘉一 様・56歳・生物学的年齢 56.0) の
  組版見本であり、受領データ (health_age 46.6) から作った例ではない。
- **アプリが医学的判断を生成すること**。ミッション④ (各診断結果を整理して伝える／独自に分析・
  解釈しない) を守る。詳細は §6。

## 2. 入力データ (2026-08-26 受領分の実測)

1 件 (1 人 1 回分の診断) = 3 ファイル。

| ファイル | 実体 | 内容 |
|---|---|---|
| `report_text.json` | dict・約 20,080 字 | 10 セクション ＋ `health_age` |
| `health_checkup.json` | dict・40 キー | `date` と `value` のみ |
| `健康アドバイスレポート_08_26.pdf` | 21 ページ | 上記 `report_text.json` の組版 |

### 2.1 `report_text.json`

```
{
  "health_age": 46.6,
  "<key>": { "section_name": "アブストラクト", "actual_chars": 608, "text": "…" },
  ...
}
```

セクション 10 件と本文の構造 (実測):

| key | section_name | 字数 | 本文の構造 |
|---|---|---|---|
| `abstract` | アブストラクト | 608 | 見出しなしの散文 |
| `summary` | 総評 | 1,005 | `### 1〜4` |
| `blood_analysis` | 検査値フィードバック | 1,585 | `【項目】` × 5 |
| `diet` | 食事アドバイス | 3,911 | `### 1〜6` ＋ `【】` 18 ＋ 箇条書き 18 |
| `exercise` | 運動アドバイス | 3,362 | `### 1〜5` ＋ 箇条書き 11 |
| `sleep` | 睡眠・ストレス管理 | 4,081 | `### 1〜4` ＋ `【】` ＋ 箇条書き 15 |
| `lifestyle` | ライフスタイル総合 | 2,982 | `### 1〜6` × `【現状評価】/【行動提案】` |
| `medical_visit` | 医療受診の目安 | 1,064 | `### 1〜4` |
| `nutrients` | 必要とする栄養素/サプリ情報 | 605 | `### 1〜3` |
| `references` | リファレンス | 1,287 | `## 出典一覧` |

### 2.2 `health_checkup.json`

```
{ "AFP [ng/mL]": [ { "date": "2026-06-08", "value": 3.9 } ], ... }
```

- キー = `項目名 [単位]`。値は `date` / `value` のみ。
- **基準値・判定・フラグは無い。**
- 日付は 1 種のみ (時系列にならない)。

### 2.3 受領 PDF は JSON の部分集合 (実測)

全 10 セクションを PDF 抽出テキストと突合した結果、**PDF に固有の情報は無い**
(JSON 19,870 字 / PDF 19,827 字、差 −43 字 ≒ 箇条書きマーカー 44 個)。

**PDF は Markdown の箇条書き構造を潰して平文にしている。** 読みやすさを作る材料として
**JSON のほうが上位**であり、入力を JSON に切り替えるのは扱いやすさだけの理由ではない。

## 3. 出力形式

| 用途 | 形式 | 方式 |
|---|---|---|
| **Web アプリでの閲覧 (正)** | **HTML** | 既存 `/report` を置き換え。Astro SSR |
| **プリントアウト / PDF 保存** | **HTML（印刷専用ビュー）** | `/report?print=1` を全展開・UI なしで出す。`@media print` は上乗せで、**それに依存しない** (§3.2〜3.3) |
| Elith 受領 PDF | PDF | **原本として保管のみ**。既定では画面に出さない |

### 3.1 なぜ PDF を生成しないか (Phase 1)

サーバ側 PDF 生成は次のコストを伴うため、**必要が生じるまで持ち込まない**:

- Vercel Serverless で Chromium を動かす必要がある (`@sparticuz/chromium` 等)。
  関数サイズと**60 秒タイムアウト** (`system_architecture_overview.md` L316) に直接効く。
- 生成物の保管・世代管理が増える (原本 S3・10 年保管の対象になるかの判断も要る)。
- **紙面が 2 系統になる** (HTML と PDF)。片方だけ直る事故が起きる。

ただし **`@media print` だけに頼るのは不可** (次項)。

### 3.2 【重要】`@media print` だけでは iPhone で成立しない

**主要利用者は 50〜65 代の経営者・役員** (UI 原則) で、閲覧はスマートフォンが主。
iOS には**結果の異なる 2 経路**があり、見つけやすいほうが印刷 CSS を通らない。

| 経路 | `@media print` | 出力 | 発見しやすさ |
|---|---|---|---|
| 共有 → **プリント** | **効く** | 印刷用レイアウト | 低 (PDF 化は更にピンチアウトが要る) |
| 共有 → **PDF** (オプションで PDF を選択) | **効かない** | 画面 CSS のままの PDF | **高** |

後者が素通りするため、次が起きる:

- ナビ・タブ・操作 UI がそのまま紙面に載る。
- **折りたたんだ本文が PDF に載らない = 中身が欠ける。** 体裁の問題ではなく欠落。

→ **`@media print` を前提にした設計は採用しない。**

### 3.3 採用方式: 印刷専用ビュー (経路非依存)

**`/report?print=1`** を用意する。

- 全セクション**展開済み**・ナビ/タブ/操作 UI なし・本文のみを、**通常の画面 CSS として**出す。
- `@media print` も併用するが、**効かなくても同じ紙面になる**ようにする (印刷 CSS は上乗せ)。
- 導線は「印刷・PDFで保存」ボタン 1 つ。押すとこのビューへ遷移し、端末別の手順を画面に出す。

これにより **共有→プリント / 共有→PDF のどちらを選んでも同じ紙面**が得られる。
ユーザーがどちらを取るかは制御できない以上、経路非依存が唯一堅い設計。追加インフラはゼロ。

**折りたたみは `?print=1` では使わない** (畳んだ状態が出力に漏れる余地を残さない)。

### 3.4 実機で確認すること (未検証)

**開発環境に iPhone が無く、Playwright の Chromium では WebKit(iOS) を再現できない。**
以下は未確認の仮説を含むため、実機で確かめる。**印刷専用ビュー方式は結果がどちらでも
成立する**ので、この確認を待たずに設計を確定してよい。

- iOS 共有 → PDF が出す PDF のページ分割 (1 枚の長大ページか、用紙サイズで分割か)。
- iOS 共有 → プリントでの `@media print` の効き (ヘッダ/フッタ・`break-inside: avoid`)。
- Android Chrome (共有 → 印刷 → PDF に保存) での同等確認。
- 表・所見カードが紙面幅で破綻しないか。

### 3.5 PDF 生成が要るのはどんなときか (Phase 2 の条件)

いずれかが確定したら実装する。**現時点ではどれも要件になっていない。**

- **表示の証跡が要る場合**。テンプレートは今後変わるので、「その日ユーザーに見せた紙面」を
  後から再現することはできない。監査要件があるならスナップショットの保存が要る。
- メール添付・郵送など、**アプリ外へ配る**運用が決まった場合。
- 面談時に**医師へ渡す**用途が決まった場合。
- **§3.4 の実機確認で、印刷専用ビューでも埋まらない差が出た場合** (用紙サイズの制御・
  ページ番号・表紙の体裁など)。これが Phase 2 の最有力の発動条件。

### 3.6 印刷 CSS の要件 (上乗せ分)

`?print=1` の画面 CSS で紙面が成立していることが前提。その上で:

- ヘッダ/フッタ (氏名・作成日・ページ番号) を `position: fixed` で入れる。
- 章の途中で切れないよう `break-inside: avoid` を所見カード・表に付ける。
- 背景色は `print-color-adjust: exact` を指定しない限り落ちる。**色だけで意味を伝えない**
  (アイコン＋テキスト＋色の 3 点セット。UI 原則と同じ)。
- **クライアント側 PDF 生成ライブラリ (html2pdf / jsPDF) は使わない。**
  和文フォントの埋め込みでファイルが肥大し、改ページ品質も低い。

## 4. 画面構成

見本の**仕掛け**のうち、受領データで誠実に成立するものだけを採る。

### 4.1 章立て

| # | 章 | 材料 | 見本のどこを参考にしたか |
|---|---|---|---|
| 0 | 表紙 | `health_age` ＋ 実年齢 ＋ `abstract` | 表紙の 2 数字並置・総括文 |
| 1 | **いちばん大事なこと** | `medical_visit` | 見本 5 章「まとめ・今後の行動指針」を**先頭へ移す** |
| 2 | 検査値でみておくこと | `blood_analysis` | 見本 1 章の所見ブロック (5 行テーブルは不成立・§6) |
| 3 | 総評 | `summary` | — |
| 4 | 食事 | `diet` | 見本 2 章 (構成の原則／推奨例／メニュー例／注意点) |
| 5 | 運動 | `exercise` | 見本 3 章 |
| 6 | 睡眠・ストレス | `sleep` | 見本 4 章 |
| 7 | 生活習慣 | `lifestyle` | 見本 1 章「生活習慣の全体的な評価」 |
| 8 | 栄養素・サプリ | `nutrients` | 見本に対応章なし (受領データにあるので載せる) |
| 9 | 出典 | `references` | 見本に対応章なし。**出典を示せることは信頼性で効く** |

**`medical_visit` を先頭に置く**のが今回いちばん効く変更。受領 PDF ではこれが 6 章目に
埋もれており、「最優先の所見」が最後まで読まないと出てこない。

### 4.2 読ませるための仕掛けと、その成否

| 見本の仕掛け | 採否 | 根拠 |
|---|---|---|
| 表紙に大きな数字 2 つ (生物学的年齢／実年齢) | **採る** | `health_age` あり。既存 `HealthAgeCard.astro` の数直線を流用 |
| 表紙に「一目で分かる要注意／良好」 | **形だけ採る** | 中身は Elith 自身の判定文から (§5.2)。全項目には広げられない |
| 所見を 5 行テーブルに構造化 | **不採用** | 5 行のうち持っているのは「原理」のみ (§6) |
| 食事・運動・睡眠を表と箇条書きへ分解 | **採る** | JSON が既に `###` と箇条書きを持つ。見本より材料が多い |
| 優先度つき行動指針の表 | **段数を減らして採る** | 「最優先」は取れる。3 段階の優先度は無い |
| 基準値と今回値の比較表・倍率 | **触れられた項目だけ採る** | 基準値は `blood_analysis` の散文中に 8 件のみ (§6) |
| がん予防の節 (1〜4 章に散在) | **不採用** | 受領テキストに「がん」が 0 件 (§6) |

### 4.3 長文の扱い

`sleep` 4,081 字・`diet` 3,911 字をそのまま流すと現状と変わらない。既存の日本語組版資産
(`src/lib/report-view.ts`) をそのまま使う:

- `paragraphizeJa()` (L59) — 2 文ごとに段落化
- `emphasizeTopicJa()` (L121) — 文頭の主題を太字化 (1 段落 1 箇所)
- `headingizeBoldLines()` (L157) — 太字だけの行を h4 へ
- 行長 38em で止める (`.md-region p / li`)

加えて **`###` 単位で折りたためるようにする** (既定は開く)。
**ただし印刷専用ビュー `?print=1` では折りたたみを使わない** — 畳んだ状態が出力に漏れると
本文が欠落するため (§3.2)。

## 5. 変換規則

**すべて決定論。LLM を通さない。** アプリは受領テキストを並べ替え・構造化するだけで、
文言を書き換えない (要約・言い換え・並べ替えをしない = ミッション④)。

### 5.1 セクションの取り込み

新形式 (dict) を既存の `ElithSection[]` (`src/lib/elith-parser.ts:10`) へ写す:

| 新形式 | 既存 |
|---|---|
| `<key>.section_name` | `section_name` |
| `<key>.actual_chars` | `char_count` |
| `<key>.text` | `text` |
| `health_age` | 別扱い (表紙) |

**`[pN]` は新形式に存在しない** (実測 0 件)。原本 PDF へのページジャンプ
(`report.astro` の `#pdf-viewer` 導線) は**成立しないので廃止する**。

### 5.2 「今回みておくこと」の抽出

`blood_analysis` の各 `【項目】` ブロックから、**Elith 自身が書いた判定文**を拾う。

- 検出語 (実測): `基準範囲を上回っています` / `基準範囲内であり` / `基準値を下回`
- 併せて、同ブロック内の `値 + （基準値：〜）` を正規表現で取り出し、値・基準値・判定を
  構造化して見出しに出す。説明文は本文として畳む。

**アプリは値と基準値を比べない。** 拾うのは Elith が明記した判定文だけ。

> **既存 `elith-report-highlights.ts` はそのままでは動かない。**
> 同ファイルは `（判定区分：X）` という Stage2 の書式に依存している (L20 `JUDGEMENT_ORDER`)。
> 新形式には `判定区分` が **0 件** (実測)。fail-safe 設計なので誤った要点は出ないが、
> **何も出なくなる**。検出ルールを上記に差し替えること。

### 5.3 検査値テーブル

- 値 = `health_checkup.json`。
- 基準値 = `blood_analysis` 本文から抽出できた 8 件のみ。**無い項目は基準値欄を空にする**
  (外部のマスタで補完しない = 捏造ゼロ)。
- **同名別値は自動採用しない** (§7)。

## 6. 作れないもの (捏造ゼロの境界)

見本にあって受領データに無い要素。**発注者判断 (2026-08-28): 受領データに無いものは作らない。**

| # | 見本の要素 | 状況 |
|---|---|---|
| ① | 要注意項目／良好な項目 | **部分的に可**。Elith の判定文がある 5 ブロックのみ。「尿検査 異常なし」等、言及外の項目に良否は付けられない |
| ② | 原理／原因／想定される疾患／悪化した場合／自覚症状 | **「原理」のみ可**。原因・病名・予後・症状は 0 件 |
| ③ | がんリスク表 (がん種／リスク要因／特記事項) | **不可**。全文 20,080 字に「がん」が 0 件。見本の「がん予防に資する運動／休養」にも波及 |
| ④ | 基準値の比較表・倍率 | **8 件のみ可**。`health_checkup.json` に基準値が無く、散文中の 8 件が上限 |

### 6.1 これは欠損ではなく方針の相違

受領テキストは判断を下さず、一貫して原票と医師へ委ねている:

> 「この所見だけでは**原因を特定することはできません**」 (`medical_visit`)
> 「血液中の赤血球成分が増加している状態であるため、**結果票にて詳細な判定内容をご確認ください**」 (`blood_analysis`)

病名 0 件・「がん」0 件・原因の断定 0 件は徹底された編集方針。**見本は Elith とは別の書き手を
前提にした設計**である。当社のミッション④とも一致するので、①〜④ を埋めない判断は方針として
整合する。

## 7. データ品質ガード

受領データ側の既知の不具合。**表示前に必ず通す。**

### 7.1 同名別値 (実測 9 組)

単位の大文字小文字だけが違い、値が別。

| 項目 | キー A | キー B | 本文が採用 |
|---|---|---|---|
| 総コレステロール | `[mg/dL]` 210 | `[mg/dl]` 251 | 251 |
| 尿素窒素 | `[mg/dL]` 27.9 | `[mg/dl]` 18.1 | 27.9 |
| 赤血球数 | `[10^4/ul]` 585 | `[万/μL]` 504 | 585 |
| クレアチニン | `[mg/dL]` 1 | `[mg/dl]` 0.96 | 0.96 |
| 尿酸 | `[mg/dL]` 4.3 | `[mg/dl]` 5.9 | 言及なし |
| 総蛋白 / 総ビリルビン / 白血球数 / 血小板数 | 同様に相違 | | 言及なし |

**扱い**: 既存の `observation-dedup` と同じ流儀で、**別値は競合として残し自動採用しない**。
画面には「値が 2 通り届いている」と出し、どちらかを勝手に選ばない。§10 で Elith に確認する。

### 7.2 本文が参照する値が JSON に無い

`blood_analysis` と `medical_visit` が**最優先の所見**として扱う **ヘマトクリット 55.6 %** の
キーが `health_checkup.json` に存在しない。**2 ファイルは包含関係にない**ので、
`health_checkup.json` だけで検査値テーブルを組むと最重要項目が落ちる。

**扱い**: 本文由来の値も表に載せ、出典 (本文/JSON) を持たせる。

### 7.3 誤字

`blood_analysis` の ALT(GPT) 項に「基準範囲を**上上回っており**」。
**アプリで直さない** (原文改変になる)。§10 で Elith に修正を依頼する。
