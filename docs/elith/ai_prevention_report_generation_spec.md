## 1. 目的

### 1.0 サービスの 2 本柱 (前提・発注者確認 2026-08-28)

Welltect の主目的は次の 2 つ。**画面設計はこの 2 本柱に従う。**

**両者は別系統ではない。1 つの検査サイクルから 2 つの出力が出る。**

```
  年 1 回 人間ドック  ＋  年 3 回 血液検査・がんリスク検査   ← 隙間を埋める
                 = 年 4 回の検査
                        │
        ┌───────────────┴───────────────┐
   A 検査結果そのもの              B その検査データで AI 診断を回す
   → 初期がんの早期発見            → 疾病予防アドバイス
```

| | 主軸 | 内容 |
|---|---|---|
| **A** | **初期がんの早期発見** | 年 1 回の人間ドックだけでは**間隔が空きすぎる**。年 3 回の検査で隙間を埋め、**年 4 回**で見ることで早期発見に繋げる |
| **B** | **AI 診断による疾病予防アドバイス** | **その年 4 回の検査データを入力に** AI 診断を回し、健康・生活改善のアドバイスを行う |

**B の入力は A の検査結果である。** 別々のデータ源ではない。

**【最重要・原則】本報告書は Elith の出力以上の表記・表現を一切しない (発注者指示 2026-08-28)。**

本報告書の役割は **Elith 出力の可読化**であり、それ以外の材料を持ち込まない。
アプリが持つスキャン結果 (腫瘍マーカー・ABC 健診・画像所見など) を報告書に並べることは**しない**。

→ **Elith の出力に A (がん早期発見) の記述が無ければ、仕様で決めた定型表現のみを出し、
詳細は「がんリスク検査の結果を見る」のリンクで別画面へ送る** (§4.0)。

**Elith は、入力にがんリスク検査があれば A について書く** (§1.0.3 で実測)。
記述の有無は Elith の怠慢ではなく**入力の違い**による。

#### 1.0.0 「Elith の原文に無い文言は紙面に出さない」の運用 (発注者指示 2026-08-29)

上の原則を**紙面の 1 文単位まで**降ろすと、こうなる。

> **紙面に出る文は、すべて受領データからの逐語であること。**
> 要約・言い換え・順序の入れ替えによる意味づけ・当社が書き足した散文は、**すべて不可**。

- **可読化は「選択」で行う。「圧縮」で行わない。** どの文を出すかを決めるのは当社の仕事だが、
  出すと決めた文は 1 文字も変えない。
  例: `lifestyle` の各節の【現状評価】【行動提案】の**冒頭 1 文をそのまま**出す
  (6 節分で紙面が成立し、全文は「詳しく読む」に残る)。
- **原文の誤字も直さない** (§7.3)。実データの「基準範囲を**上上**回っており」はそのまま出す。
- **構造ラベルはこの規則の対象外。** カード見出し・表の列見出し (項目／今回／基準値／判定)・
  表紙の項目名・ナビゲーションのラベルは**文ではなく枠**であり、Elith の原文には存在し得ない。
  ただし**対応する `section_name` や `###` 見出しがある場合はそれを使う**
  (例: 「医師に相談する項目」ではなく「医療受診の目安」)。当社が言い換えた見出しを作らない。
- **原文に無い判定は付けない。** 判定欄は Elith の判定句を逐語で置き、Elith が判定を書いて
  いない項目は空 (`—`) にする。「記載なし」等の当社の語を入れない。

**唯一の例外 (パイロット版 v0.1 のみ)**

| 箇所 | 扱い |
|---|---|
| タイプ 2 の主軸 A「今回の所見」カードの 2 文 | **現状のまま置く。** Elith へ出力を依頼中の文型 (§10.1 E-1) であり、受領データにはまだ無い。パイロット版で Wellfort・Elith に確認し、回答を得てから修正する |

この例外は**依頼の内容をそのまま見てもらうため**に置いている。確定したら
Elith 出力へ差し替えるか、`ui.cancer_screening_not_included` (§4.0.1) の定型文へ落とす。

### 1.0.1 発行タイミング (最上位プラン)

**年 4 回発行される。** ①ユーザーが人間ドック報告書をスキャン投稿した後、
②③④ 血液検査・がんリスク検査の実施タイミング。

- **回によって材料が違う。** ①は腫瘍マーカー・ABC健診・画像所見を持つが、②〜④は持たない。
  → **材料が無い章は出さない**を第一級の要件とする (§1.3.2 のレジストリで空章を落とす)。
- **表示は常に最新版 1 件**。過去分はアーカイブとして閲覧可能なレベルに留める
  (現行 `status='superseded'` ＋ 最新 1 件取得のままでよい。**訂正版は考慮しない**)。
- 紙面に **「第 N 回」** を印字する。端末に年 4 通たまるため (§3.6)。

### 1.0.2 時系列はアプリで作らない (発注者判断)

**Elith は過去の診断データを保持し、最新診断時に常に参照した上で報告書を生成している。**
したがって前回との差分・推移の解釈は**受領テキストに織り込み済み**。

→ **アプリが前回比・推移グラフを別途組み立てない。** 二重の解釈になる。
アプリのミッションは**最新版を正しく伝えること**。

### 1.0.3 【重要】報告書は 2 タイプある — 購入形態で入力が変わる

**どちらも正しい。** A の章の見え方が変わる。

| | **タイプ 1: コースプラン** | **タイプ 2: 単品購入** |
|---|---|---|
| 対象 | **全コースプラン** | AI疾病予防報告書のみを単品購入 |
| Elith への入力 | 人間ドック ＋ 血液検査 ＋ **がんリスク検査** ＋ AI 問診 | **自分でスキャンした人間ドック ＋ AI 問診のみ** |
| Elith の出力 | **がんについて書く** | がんリスク評価は含まれない |
| A の章 | **Elith の記述をそのまま出す** | **定型表現のみ**（§4.0.1） |

#### 実測での裏付け (2 検体)

| 検体 | がんリスク検査 | Elith 出力の「がん」言及 |
|---|---|---|
| 2026-08-26 受領 (合成検体) | **入力に無し** | 「がん」「腫瘍」「マーカー」**すべて 0 回** |
| 2026-08-06 Stage2 (別人) | **入力に有り** | **「がん」7 回・「腫瘍マーカー」「PSA」に言及** |

Stage2 検体の実際の記述:

> 今回の検査結果では、**腫瘍マーカーの PSA が健康な判定**であり、**がんリスク評価においても
> 低リスクの範囲**を示しているという良好な点があります。（総評 §1）

> また、がんリスク評価については低リスクの範囲を示していますが、**これはがんがないことを
> 断定するものではない**ため、定期的な確認を大切にすることがあなたにとって重要です。

**→ Elith は「がんがないことの断定ではない」という但し書きも自分で書いている。**
タイプ 1 では**当社が但し書きを足す必要がない**。

#### 実装上の含意

- **A の章が空になるのは異常ではない。** タイプ 2 では正常な状態。
  「Elith が書き忘れた」と誤解して当社が補完しないこと。
- **タイプの判定はアプリが持つ**（その回の入力にがんリスク検査が含まれたか）。
  Elith の出力から推測しない。
- 現状 Elith の記述は**「総評」の中に他の話と混ざって**入っている (Stage2 検体)。
  A の章に切り出すには散文からの抽出が要るため、**独立フィールドの依頼 (§10.1 E-1) は
  今回の発見でより必要性が上がった**。

### 1.1 目的

**Elith の出力は文章の羅列で、一般ユーザーが読み通せない。** 読みやすく、重要な点が確実に伝わる
報告書を、受領データから**アプリが生成する**。

- **入力の正 = JSON** (`report_text.json` / `health_checkup.json`)。
- **見本 PDF (`AI疾病予防レポート` 18p) = 様式のお手本**。埋めるべき項目の一覧ではなく、
  **見せ方**(表紙の作り・章立て・表への落とし込み・視覚的な優先順位) を参考にする。
- **Elith の PDF = 原本**。表示の主役から外し、監査用に保管する。

### 1.2 非目的 (やらないこと)

- 見本 PDF の**内容**を再現すること。見本は別検体 (田宮嘉一 様・56歳・生物学的年齢 56.0) の
  組版見本であり、受領データ (health_age 46.6) から作った例ではない。
- **アプリが医学的判断を生成すること**。ミッション④ (各診断結果を整理して伝える／独自に分析・
  解釈しない) を守る。詳細は §6。

### 1.3 【最重要】設計方針 — 変更され続ける前提で作る

**この報告書は本アプリの肝であり、クライアント・ユーザーの双方から改善要望が絶えず出る前提で
設計する。** 「一度作って終わり」の画面として実装してはならない。

要望のたびに `.astro` を開いて構造を組み替える作りにすると、次のことが起きる:

- 章を 1 つ増やす／順序を変えるだけでコード変更・レビュー・デプロイが必要になり、要望が滞留する。
- 画面と印刷ビューが別々に育ち、片方だけ直る (§3.3 で潰した二重管理が再発する)。
- Elith 側の出力変更に追随できない。**すでに 1 度起きている** —
  Stage2 の `（判定区分：X）` に依存した `elith-report-highlights.ts` は、
  新形式で**無言で空になる** (§5.2)。

そこで、以下を**実装上の制約**とする。

#### 1.3.1 要望の 3 分類と、対応コスト

新しい要望が来たら、まずどれかに仕分ける。**仕分けが設計を守る。**

| 種別 | 例 | 対応 |
|---|---|---|
| **(a) 見せ方** | 章の順序・表示可否・見出し文言・既定の開閉・注意書き | **コード変更なし**。`app_config` を admin から変更 (§1.3.2) |
| **(b) 構造** | 章を追加・新しいデータ源・表の列を増やす | アダプタとレンダラの追加。既存章に影響を出さない |
| **(c) 内容の創作** | 「原因も書いて」「がんリスクも出して」「良否を判定して」 | **不可**。受領データに無いものは作らない (§6)。**断る根拠を §6 に置いてある** |

**(c) を (a)(b) のふりをして受けないこと。** 要望の圧が最も強く出るのは (c) なので、
仕様書のこの表を根拠に会話する。

##### 実例: 表現手法の外部提案をどう仕分けたか (2026-08-28)

伝え方の改善案 (動機づけ面接・選択肢提示・短期実験・スティグマ回避など) を外部レビューで得た。
**大半は「AI が助言文を書く」前提**で、アプリ側では (c) に当たる。
**発注先を Elith に移せば (b) 以下になる**、という仕分けをした。

| 提案 | 判定 |
|---|---|
| 変えなくてよいものも伝える | **採用**。`lifestyle` の【現状評価】【行動提案】をペアで出せば実現 (§4.2.2) |
| 短期実験として提示する | **採用**。`diet` §4 の「1 か月の食事改善プラン」が既に段階計画になっている |
| 最も効くレバーを示す | **採用**。ただし当社が算出せず **Elith の「最優先の所見」**を使う |
| 選択肢として提示する | **一部採用**。Elith の行動提案をチェックできる UI にする。**「1 つ選べ」という指示文は書かない**（Elith は全項目に「してください」と書いており、当社が優先順位を付け直すことになる） |
| 反発を先に認める前置き | **不要**。`abstract` が既に穏やかな入り方をしている。自前の前置きを書かない |
| スティグマ回避 | **採用**。当社の固定文言の規則にする (§4.2.1) |
| 既定トーン＝結論と数字を端的に | **採用**。当社 UI 原則と一致 |
| 「やめる」→「交換する」の言い換え | **不可**。Elith の文の書き換え (§5 冒頭) |
| 価値観を選ばせて説明を変える | **不可**。分岐ごとの文章生成になる |
| トーン 4 版 | **不可**。4 通りの文章＝生成 |

**外部提案の具体例は当社検体に合わないことがある** — 上記レビューは実データを見ずに書かれており、
飲酒・揚げ物・腹囲を前提にしていたが、この検体は非飲酒・非喫煙で腹囲の記載も無い。
**提案は手法として読み、内容は必ず実データに当てて検証する。**

#### 1.3.2 章立てを設定に出す (コードに埋めない)

章の **key / 表示名 / 出力元 / 順序 / 既定の開閉 / 印刷に載せるか** をレジストリとして持ち、
**`.astro` にハードコードしない**。

- **コード既定のレジストリ**を持ち、**`diagnosis.app_config` で上書きできる**ようにする。
  優先順位は既存の流儀どおり **DB値 → コード既定** (`src/lib/app-config.ts`)。
- 設定値の置き場所の判断基準は**秘匿性** (CLAUDE.md 確定事項)。章立て・文言は秘匿性が低く
  切り替えが想定されるので **`app_config` が正しい置き場所**。env に置かない。
- 既存の前例に倣う: `ui.support_contact` / `ui.health_age_followup`
  (`app-config.ts:33,35`)。**既定は空・空なら出さない** = 架空の文言を作らない流儀も踏襲する。
- admin UI は **wellfort-site 側**に置く (Scan-Chat-AI は API 提供側。CLAUDE.md 確定事項)。

これにより **(a) の要望は「デプロイ不要・admin から即時」** になる。反映は TTL 45 秒。

#### 1.3.3 受領形式と表示モデルを分ける

**`受領JSON → 表示モデル(ViewModel) → レンダラ`** の 3 層にし、層をまたいだ直参照を作らない。

- **Elith の形式変更はアダプタ 1 枚で吸収する。** 画面側は表示モデルしか知らない。
- Stage2 → Stage3 で実際に形式が変わった (`判定区分` と `[pN]` が消えた) 実績があるため、
  **次も変わる前提**で置く。
- 表示モデルは型を持つ (`ElithSection[]` に押し込めず、章・所見・値の構造を素直に表す)。

#### 1.3.4 変換規則は 1 箇所に集約する

受領テキストからの抽出・整形は**単一のモジュールが所有する**。`.astro` に正規表現を散らさない。

本リポジトリには既に同じ規律の前例がある —
納品整形は `elith-export.ts` の `sanitizeMeasurementsForDelivery()` に集約し、
「二重管理しない」と CLAUDE.md に明記されている。**それと同じ扱いにする。**

#### 1.3.5 画面と印刷は同じレンダラから出す

`?print=1` は**モード引数**であって別実装ではない (§3.3)。
**章を 1 つ足したら印刷ビューにも自動で載る**こと。載らない実装にしない。

#### 1.3.6 抽出できなかったことを可視化する

フォーマット依存の抽出 (§5.2) は **fail-safe (拾えなければ何も出さない)** を維持する。
ただし現状は**黙って空になる**ので、それだけでは気づけない。

→ **抽出監査を admin に出す** (どの章を認識し、何件の所見を拾い、何を拾えなかったか)。
スキャン側の `vqa_audit` と同じ流儀。**納品/表示データには混ぜない。**

#### 1.3.7 回帰を機械で担保する

本リポジトリの流儀 (🎯ゴールデン) をここにも適用する。

- 受領 JSON を fixture として置き、**表示モデルのスナップショット**を比較する。
- 担保したいのは主に **「文言を書き換えていないこと」** (要約・言い換え・並べ替えをしない
  = ミッション④)。章の並べ替えや設定変更で本文が変質していないかを機械で見る。

#### 1.3.8 表示名は「ウェルネス年齢」— 内部識別子と混同しない

正本: `docs/scan/health_age_simple_v7.0_spec.md §0` / CLAUDE.md 確定事項。

> **「健康年齢」→「ウェルネス年齢」。画面・帳票・ドキュメントの表示名はすべて
> 「ウェルネス年齢」。内部識別子は据え置き。**

受領 JSON のキーが `health_age` なのは**内部識別子だから据え置き**なのであって、
**画面に「健康年齢」と出してよい理由にはならない。** Elith 由来の値でも、
表示する以上は **ウェルネス年齢**。ラベルは `wellness-age.ts` の
`WELLNESS_AGE_LABEL` を参照し、文字列を直書きしない。

**表示するのは Elith 出力の値のみ。** 併記もしない。

**なぜ一致するのか**: ウェルネス年齢は**アプリが CABA で算出し、`HealthAgeData` として
Elith へ渡している** (`elith-assemble.ts:273`)。**Elith 側は計算していない**ので、
受領 JSON の `health_age` は**アプリが渡した値がそのまま返ってくる**。したがって**本来は必ず一致する**。

- 2026-08-26 受領分で当社 CABA と値が一致しなかったのは、**合成検体によるイレギュラー** (§7.0)。
  設計上の問題ではない。
- → **不一致は異常。** 表示は Elith 出力に従いつつ、**当社の算出値と突き合わせて
  不一致なら抽出監査に出す** (§1.3.6)。往復のどこかでデータが壊れた兆候として使える。

**ただし本報告書の画面版には出さない。** 置き場所は §4.0.0.3。

#### 1.3.9 紙面テンプレートに版を持たせる

紙面を変えたらテンプレート版を上げ、**紙面に印字する** (§3.8)。
端末に保存された控え (§3.6) は回収できないため、**どの版の紙かを紙自身が名乗る**必要がある。

### 3.1 サーバ側 PDF 生成 — **必要** (発注者判断 2026-08-28)

**PDF ファイルを生成する。** 以前「必要が生じるまで持ち込まない」としていた判断は**撤回**。

#### 生成タイミング: **表示時ではなく、取込時に 1 回**

これが設計の要。オンデマンド生成は Vercel の制約に正面からぶつかる。

| | 都度生成 (不採用) | **取込時に 1 回 (採用)** |
|---|---|---|
| 60 秒タイムアウト | 表示のたびに Chromium 起動＝危険 | **表示経路に Chromium が入らない** |
| 生成コスト | 閲覧回数ぶん | 報告書 1 件につき 1 回 |
| 証跡 | 残らない | **その日の紙面がそのまま残る** (§3.5 の証跡要件を自動的に満たす) |
| 版ずれ | 常に最新テンプレで再生成 | 発行時点のテンプレで固定 → **紙面の版と一致** (§1.3.9) |

- **取込 API (`api/admin/elith-report/upload.ts`) の中で、HTML を組んで PDF 化し S3 へ保存する。**
  失敗しても取込自体は成功させる (PDF は後から admin で再生成できるようにする)。
- **admin から再生成できるようにする。** 章立て (`app_config`) を変えたときに作り直せる。
- 保存先は原本ストレージ (`putOriginal()`)。**Elith 受領 PDF とは別物**なので混ぜない
  (受領 PDF = `report_pdf_url`、生成 PDF = 新カラム)。

#### 実装手段

- `@sparticuz/chromium` + `puppeteer-core` を**取込経路にのみ**入れる。
  表示経路の関数サイズには影響させない (Astro のルート単位で依存を分ける)。
- 入力は **`?print=1` の HTML** (§3.3)。**画面・印刷・PDF が同じレンダラから出る**ので
  紙面が 3 系統に割れない (§1.3.5)。
- **未検証**: Vercel Serverless での Chromium 起動時間と関数サイズは実測が必要。
  パイロット版で計測し、収まらなければ別サービスへ切り出す。

#### 「ファイルに保存」との関係

§3.6 の「共有 → PDF で『ファイル』アプリへ」は**引き続き有効**。
生成 PDF があれば**ワンタップの「PDF を保存」ボタン**を出せるので、
共有シートを辿らせる導線は**補助**に降りる (50〜65 代には大きい)。

### 3.2 【重要】`@media print` だけでは iPhone で成立しない

**主要利用者は 50〜65 代の経営者・役員** (UI 原則) で、閲覧はスマートフォンが主。
iOS には**結果の異なる 2 経路**があり、見つけやすいほうが印刷 CSS を通らない。

| 経路 | `@media print` | 出力 | 発見しやすさ |
|---|---|---|---|
| 共有 → **プリント** | **効く** | 印刷用レイアウト | 低 (PDF 化は更にピンチアウトが要る) |
| 共有 → **PDF** (オプションで PDF を選択) | **効かない** | 画面 CSS のままの PDF | **高** |

後者が素通りするため、次が起きる:

- ナビ・タブ・操作 UI がそのまま紙面に載る。
- **折りたたんだ本文が PDF に載らない = 中身が欠ける。** 体裁の問題ではなく欠落。

→ **`@media print` を前提にした設計は採用しない。**

### 3.3 採用方式: 印刷専用ビュー (経路非依存)

**`/report?print=1`** を用意する。

- 全セクション**展開済み**・ナビ/タブ/操作 UI なし・本文のみを、**通常の画面 CSS として**出す。
- `@media print` も併用するが、**効かなくても同じ紙面になる**ようにする (印刷 CSS は上乗せ)。
- 導線は「印刷・PDFで保存」ボタン 1 つ。押すとこのビューへ遷移し、端末別の手順を画面に出す。

これにより **共有→プリント / 共有→PDF のどちらを選んでも同じ紙面**が得られる。
ユーザーがどちらを取るかは制御できない以上、経路非依存が唯一堅い設計。追加インフラはゼロ。

**折りたたみは `?print=1` では使わない** (畳んだ状態が出力に漏れる余地を残さない)。

### 3.4 実機で確認すること (未検証)

**開発環境に iPhone が無く、Playwright の Chromium では WebKit(iOS) を再現できない。**
以下は未確認の仮説を含むため、実機で確かめる。**印刷専用ビュー方式は結果がどちらでも
成立する**ので、この確認を待たずに設計を確定してよい。

- iOS 共有 → PDF が出す PDF のページ分割 (1 枚の長大ページか、用紙サイズで分割か)。
- iOS 共有 → プリントでの `@media print` の効き (ヘッダ/フッタ・`break-inside: avoid`)。
- Android Chrome (共有 → 印刷 → PDF に保存) での同等確認。
- 表・所見カードが紙面幅で破綻しないか。

### 3.5 PDF 生成で満たされる要件

§3.1 で生成すると決めたことにより、以下が同時に満たされる。

- **表示の証跡**: 発行時点の紙面がファイルとして残る。テンプレート変更後も再現できる。
- **アプリ外への配布**: メール添付・郵送・医師への提示。
- **ワンタップ保存**: §3.6 の手順を辿らせずに済む。

### 3.6 端末に残す (オフライン対応) — 発注者判断 2026-08-28

#### 要件と、その根拠

**オフラインで見たいのは「AI疾病予防報告書」だけ。** アプリ全体のオフライン対応は対象外。

理由 (発注者):

- **他の検査報告書は紙でユーザーの手元に届く。** 検診・人間ドック・がんリスク・遺伝子・血液は
  いずれも実物が手元に残る。
- **この報告書だけは、アプリからしか入手できない。** 紙の代替物が存在しない。
- **この報告書が本 Web アプリの肝**であり、「見たいときに見られない」が最も起きてはならない。

→ **報告書 1 点を端末に恒久的に残せること**が要件。アプリ全体をオフラインで動かすことではない。

#### 採用方式: A. ファイル (PDF) として「ファイル」アプリに保存

印刷専用ビュー (§3.3) → 共有 → PDF 形式で「ファイルに保存」。

| | |
|---|---|
| 保存先 | iOS「ファイル」アプリ (iCloud Drive / この iPhone 内)。**ブラウザのストレージの外** |
| 消えるか | **消えない。** ブラウザのデータ削除・ITP のストレージ破棄の対象外 |
| オフライン | **完全に可**。アプリを開く必要すらない |
| 二次利用 | 医師へ提示・家族へ共有・印刷、いずれも可 |
| 追加インフラ | **ゼロ**。§3.3 の印刷専用ビューをそのまま使う |

**「都度サーバーから DL したくない」に最も素直に応える。1 回保存すれば以後アプリ不要。**

#### UI 導線の要件

主要利用者は 50〜65 代。**「共有 → オプション → PDF → ファイルに保存」を自力で辿らせない。**

- 報告書画面に **「iPhone に保存する」** を独立した導線として置く (印刷と並べない・埋もれさせない)。
- 押すと印刷専用ビューへ遷移し、**端末を判定して手順を画面に出す** (iOS / Android / PC)。
- 手順はスクリーンショットではなく短い文章で。OS 更新で文言が変わるため、
  **メニュー名を断定せず「共有ボタン（□に↑）」のように形で示す**。

#### 保存した控えは「その時点のスナップショット」

Elith が報告書を再発行すると (`status='superseded'`)、端末の控えは古くなる。**回収も更新もできない。**

- 紙面に **作成日と版** を必ず印字する (§3.7 の印刷ヘッダ/フッタ要件)。
- アプリ側で新しい版を受領したら、報告書画面に「新しい報告書が届いています」を出す。
- **古い控えを消す手段は無い**前提で設計する (消せると誤解させる UI を作らない)。

#### なぜ Service Worker でキャッシュしないか

技術的には可能だが、**この要件に対しては割に合わない**:

1. **iOS のストレージ破棄の扱いが読めない。** Safari は一定期間アクセスの無いサイトの
   script-writable storage (Cache API / IndexedDB 等) を破棄する。ホーム画面に追加した
   Web アプリは対象外とされるが、**これは Apple 側の変更が続く領域で、記憶を根拠にできない**
   (R3)。採用するなら WebKit 公式で裏を取る必要がある。**「消えないはず」で設計して消えると、
   いちばん見せたいものが消える。**
2. **認証と噛み合わない。** `/report` は SSR で、サーバーがユーザーを解決している
   (`report.astro:32` `prerender = false` / `astro.config.mjs:7` `output: 'server'`)。
   オフラインで出すにはキャッシュ済み HTML を**認証を通さずに返す**しかなく、
   **端末のロックさえ解ければ他人の検査結果が読める**状態になる。
3. **実装量が大きい。** SW ライフサイクル・更新戦略・ユーザー別のキャッシュ分離・
   古い報告書を掴み続ける事故の防止。**報告書 1 点を残すだけなら A で足りる。**

#### ただし Service Worker は入れる (用途を絞って)

現状 **SW は存在しない** (`grep` ヒット 0)。一方 `manifest.webmanifest` は
`display: standalone` なので、**ホーム画面から起動すると「アプリの見た目で Safari のエラー画面」**
になる。アプリらしく見えるぶん体験としてはむしろ悪い。

→ **オフライン時に「通信がありません／保存済みの報告書はファイルアプリにあります」と案内する
だけの最小の SW を入れる。** 報告書本体はキャッシュしない (上記 1〜3 を踏まない)。

#### 実機で確認すること

- 共有シートから PDF 形式で「ファイルに保存」した紙面が、印刷専用ビューどおりか。
- 保存された PDF のページ分割 (§3.4 と同じ確認)。
- Android (Chrome → 印刷 → PDF に保存 → ファイル) での同等確認。

### 3.7 印刷 CSS の要件 (上乗せ分)

`?print=1` の画面 CSS で紙面が成立していることが前提。その上で:

- ヘッダ/フッタ (氏名・**作成日**・**版**・ページ番号) を `position: fixed` で入れる。
  端末に保存された控えが古いかどうかを、その紙だけで判別できるようにするため (§3.6)。
- 章の途中で切れないよう `break-inside: avoid` を所見カード・表に付ける。
- 背景色は `print-color-adjust: exact` を指定しない限り落ちる。**色だけで意味を伝えない**
  (アイコン＋テキスト＋色の 3 点セット。UI 原則と同じ)。
- **クライアント側 PDF 生成ライブラリ (html2pdf / jsPDF) は使わない。**
  和文フォントの埋め込みでファイルが肥大し、改ページ品質も低い。

## 4. 画面構成

報告書は **A（初期がんの早期発見）→ B（AI 診断による疾病予防アドバイス）** の順で構成する (§1.0)。

### 4.-1 【最上位】2 本柱の帯は常設 — 章の出し分けより上位

**設計ポリシー (Wellfort へ提示済み)**:

> 報告書の冒頭には、サービスの 2 本柱をそのままトピックとして置きます。
> ① がん早期発見 ② 疾病予防アドバイス
> 章の並び・見出しも、この 2 本柱に沿えて構成しました。

→ **軸の見出しは報告書の骨格であり、章ではない。**
表紙と同じ理由で**レジストリに入れない**。並べ替えも非表示もしない。
§0.3「材料が無い章は出さない」は**中身 (所見カード) にだけ**かかる。

**実装事故 (2026-08-29・修正済)**: 当初これを描かず、`axis` を配列を分けるための変数に
しか使っていなかった。結果、A に材料が無い検体 (タイプ 2 = パイロットの対象) で
「材料が無い章は出さない」が働き、**A 軸の痕跡がゼロ**になって報告書が B から始まっていた。
モックでは軸の帯と所見カードは別要素で、「実運用では非表示」の注記は**カード側**に付けていた。
それを 1 つの章に潰したのが原因。**枠 (軸) と中身 (章) を分けること。**
定義は `src/lib/report-sections.ts` の `REPORT_AXES`。

#### 【重要】ポリシーの説明文を紙面に載せない (2026-08-29 追加修正 その 2)

**設計ポリシーの本文をそのまま画面に貼るのは誤り。**
「年 1 回の人間ドックの隙間を年 3 回の検査で埋め、年 4 回で早期発見につなげます」
「Welltect は次の 2 つを柱にしています。この報告書も、その順で構成しています」は
**Wellfort に設計意図を説明するための文**であって、報告書の中身ではない。
紙面に置けば **当社が書いた散文**になり、§1.0「報告書は Elith の出力以上の表記・表現を
一切しない」に正面から反する。要望の 3 分類 (§1.3.1) でいえば **(c) 内容の創作 = 不可**。

**ポリシーが求めているのは「2 本柱が構造として最初に見えること」**であって、
ポリシー文の掲載ではない。→ 冒頭に置くのは**見出しとリンクだけ**。
`REPORT_AXES` は `key` と `title` しか持たない (リードを持たせない)。

#### 冒頭に置く (2026-08-29 追加修正 その 1)

設計ポリシーは「**冒頭**に 2 本柱をそのままトピックとして置く」。軸の帯を描くだけでは足りず、
**画面を開いた最初に見えていること**が要件。当初の並びは

```
表紙 → 手元に残す → 目次 → 主軸A → 主軸B     ← 2 本柱が保存導線と目次の下に埋もれる
```

となっていた。次の並びに直した。

```
表紙(識別) → 【目次 = 2 本柱＋章名リンク】 → 総括文 → 手元に残す → A 見出し → B 見出し
```

- **目次を軸ごとに組み直し、それ自体を「冒頭トピック」にした。** 章名は軸の下にぶら下げる

### 4.2.2 生活習慣は「現状 → 提案」のペアで出す（分類しない）

`lifestyle` は Elith が 6 項目それぞれを【現状評価】【行動提案】に分けて書いている。
**そのままペアで並べる。**

> **飲酒**　現在はまったく飲酒していない → そのまま続ける
> **喫煙**　過去に喫煙、現在は吸っていない → そのまま保つ
> **仕事中**　1 日の座位 8 時間 → 座り続けない過ごし方を加える

**維持／改善の自動分類はしない。** 語尾での判別を実験したところ、「続け**ながら**」が
語彙リストに一致せず取りこぼした。**リストの作り方次第で結果が変わる = 脆い判定**
(スキャン側で繰り返した失敗と同型)。ペアで出せば読者が自分で判別でき、当社は誤りようがない。

年 4 回発行されるため (§1.0.1)、同じ助言の反復に見えやすい。
**続けられている項目がそのまま出ること自体が価値**になるので、維持系を隠さない。
未確認の項目 (この検体では通勤・余暇) も正直に出す。

### 5.4 トピック抽出と「詳しく見る」

受領テキストは章内が見出しで区切られているので、**トピック一覧を機械生成できる**。

|---|---|---|
| `### N. 見出し` | 総評 4 / 食事 6 / 運動 5 / 睡眠 4 / 生活習慣 6 / 受診 4 / 栄養素 3 | 32 |
| `【項目】` | 検査値フィードバック | 5 |
| 見出しなし | アブストラクト / リファレンス | 2 (章まるごと 1 トピック) |

- 各トピック = **見出し + 冒頭 1 文 (原文のまま) + アンカー**。

- アンカー ID は `セクションkey + 見出しのハッシュ` で決定論的に生成する
  (連番にすると章を並べ替えたときにリンクが壊れる)。

### 5.5 LLM を使うか — 使わない (2026-08-28 精査)

**結論: トピック抽出に LLM は使わない。** 決定論で 39 件中 38 件が実用水準に達しており、
LLM の限界効用が小さい一方、リスクが大きいため。

#### 実測

冒頭 1 文が抜粋として不適切なものは **39 件中 1 件のみ**
(`栄養素/優先栄養素と理由` →「優先候補は食物繊維です。」= 短いだけで誤りではない)。
**LLM を入れて改善できるのは実質 1 トピック。**

#### LLM が得意な領域は、そもそも禁止事項と重なる

| LLM に期待できること | 可否 |
|---|---|
| 章の要点を**書き起こす** | **不可**。原文に無い文を作る = ミッション④違反・捏造 |
| 「この人にとって重要な 3 点」を**選んで順位づけ** | **不可**。医学的な重み付け = 判断。しかも Elith が既に「最優先の所見」を明示している |
| 読みやすく**言い換える** | **不可**。要約・言い換え・並べ替えをしない (§5 冒頭) |
| 抜粋する 1 文を**選ぶ** | 技術的には可。ただし上記のとおり効果は 1 件 |

#### 本リポジトリの実績 (これが決め手)

スキャン側で LLM を後段に置いた結果、繰り返し捏造と非決定を踏んでいる:

- **多数決 (N-run) は撤回** — 名称が run 毎に揺れて union が膨張 (rows95→123・重複15・捏造5)。
- **perception repair の `inventoryReread`** — 好中球/LDH/受診コース等を**幻覚して 5 件 push**。
- **VQA 充填** — K-W の無い様式で 0 を push し**捏造 4 件**。
  → 確定ルール **「VQA充填は新規pushしない = 既存空行のみ充填」** に至った。

**このルールはそのまま本機能にも効く: LLM に新しいものを作らせない。**

#### それでも将来 LLM を入れるなら (満たすべき条件)

要件が変わって導入する場合は、以下を**全て**満たすこと。

1. **選択のみ・生成禁止。** 出力は「原文のどの範囲か」であって、新しい文ではない。
2. **verbatim 検証を機械で行う。** 返ってきた文字列が原文の部分文字列でなければ**採用せず
   決定論版へフォールバック** (`sourceText.includes(quote)`)。信頼ではなく構造で担保する。
3. **取り込み時に 1 回だけ実行し、結果を DB に保存する。** 表示のたびに呼ばない。
   - 同じ報告書が読むたびに違う内容になるのを防ぐ (画面と印刷の不一致も防ぐ)。
   - Vercel の 60 秒制限に表示経路を晒さない (スキャン側で実際に 504 を踏んでいる)。
4. **どのトピックが LLM 選択かを監査に出す** (§1.3.6)。
5. **app_config のフラグで既定 off** (`report.llm_topic_pick`)。スキャンの精度フラグと同じ運用。

#### 検査値テーブルで踏んだ 2 つの実装バグ (どちらも回帰チェックで検出)

1. **単位の大小文字を潰すと 2 検体が混ざる。** 突き合わせキーを `toLowerCase()` していたため
   `mg/dL`(血液検査) と `mg/dl`(人間ドック) が同一視され、**Elith が判定していない行に判定が付いた**
   (§7.0 の合成検体の規則を潰していた)。→ 空白だけ落として大小はそのまま比べる。
2. **単位の切り出しが数字を食う。** `value.replace(/^[\d.,\s]+/, '')` は `585 10^4/ul` の
   単位側の `10` まで消して `^4/ul` にしていた。→ `/^[\d.,]+\s*/`。

判定の割り当ては **Elith が名指しした項目にだけ**当てる。
「クレアチニンについても基準値との関係において…」のように判定句を伴わない言及には付けない
(実測: クレアチニンの判定は空のまま = Elith は判定を書いていない)。

#### 9.3.1 v0.1.1 — 主軸 B が白紙になった不具合 (2026-08-29・実データで発覚)

**症状**: 本番の検体 (`/report?u=d0000001-…`) で **主軸 B「AI 診断による疾病予防アドバイス」が
帯だけ**になり、ダイジェストのカードが 1 枚も出なかった。全編には 10 章すべてが出ていた。

**原因は 3 つとも「受領形式の世代差を認識できていない」もので、内容の不足ではない。**
出せる文が実際にあるのに拾えていなかった。実測 (本番 HTML から採取):

| # | 世代差 | 実装の前提 | 実測 | 影響 |
|---|---|---|---|---|
| ① | `検査値フィードバック` の節が `###` | `buildMeasurements` が `splitByBracket` 決め打ち | `【` **0 件** / `###` **8 件** | ブロック 0 → 表が空 |

**なぜ気づけなかったか**: ダイジェストの抽出は fail-safe (拾えなければ何も出さない) なので、
**誤った要点を出す代わりに黙って空になる**。§1.3.6 が予告していた failure mode そのもの。
検証はサンプル (2026-08-26 受領分) だけで行っており、**本番 DB の別世代の検体を通していなかった**。

**対処 (すべて「認識の拡張」で、中身は作っていない)**:

1. `VALUE_RE` … `基準値[：:]` の両方を受ける。
2. `buildMeasurements` … `splitByBracket` 決め打ちをやめ `splitTopics` (`###` → `【】`) 経由へ。
   見出しがまったく無い章は**章まるごと 1 ブロック**として扱う (`topicsOrWhole`)。
3. `medical_visit` / `nutrients` … 見出しが無い世代では**章の冒頭 2 文**を出す。
   全編の章側は元からこの受け皿を持っていた (「見出しの無い章は章まるごと 1 トピック」) が、
   ダイジェスト側に無かった。出典表記も `§1〜§N` ではなく `冒頭 2 文` と書き分ける。
4. `lifestyle` … **直さない。** 【現状評価】【行動提案】が無い世代でペアを組むには
   「どの文が現状でどの文が提案か」をアプリが決めることになり、それは解釈 (ミッション④)。
   この世代では空のままにし、本文は全編に出す。
5. **軸が空でも黙らない** (`report.astro`)。ダイジェストが 0 枚の軸には、全編があれば
   「今回の受領分からは要点を取り出せませんでした。本文は下の『全編』にすべてあります。」、
   材料そのものが無ければ「今回はこの項目の材料が届いていません。」を出す。
   **当社が代わりの要点を書かない** (§1.0.0)。

**回帰**: 本番検体と同じ形 (`###` 節 ＋ 半角コロン ＋ 見出しの無い章) の fixture を
`verify-report-model.ts` に追加し、**主軸 B のカードが 3 枚以上出ること・
`最高血圧` の基準値 `〜129 mmHg` が結べること・旧世代でも紙面の文が全部逐語であること**を固定した。
**74 / 74 件**。
