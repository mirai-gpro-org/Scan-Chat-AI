## 1. 目的

**Elith の出力は文章の羅列で、一般ユーザーが読み通せない。** 読みやすく、重要な点が確実に伝わる
報告書を、受領データから**アプリが生成する**。

- **入力の正 = JSON** (`report_text.json` / `health_checkup.json`)。
- **見本 PDF (`AI疾病予防レポート` 18p) = 様式のお手本**。埋めるべき項目の一覧ではなく、
  **見せ方**(表紙の作り・章立て・表への落とし込み・視覚的な優先順位) を参考にする。
- **Elith の PDF = 原本**。表示の主役から外し、監査用に保管する。

### 1.1 非目的 (やらないこと)

- 見本 PDF の**内容**を再現すること。見本は別検体 (田宮嘉一 様・56歳・生物学的年齢 56.0) の
  組版見本であり、受領データ (health_age 46.6) から作った例ではない。
- **アプリが医学的判断を生成すること**。ミッション④ (各診断結果を整理して伝える／独自に分析・
  解釈しない) を守る。詳細は §6。

### 1.2 【最重要】設計方針 — 変更され続ける前提で作る

**この報告書は本アプリの肝であり、クライアント・ユーザーの双方から改善要望が絶えず出る前提で
設計する。** 「一度作って終わり」の画面として実装してはならない。

要望のたびに `.astro` を開いて構造を組み替える作りにすると、次のことが起きる:

- 章を 1 つ増やす／順序を変えるだけでコード変更・レビュー・デプロイが必要になり、要望が滞留する。
- 画面と印刷ビューが別々に育ち、片方だけ直る (§3.3 で潰した二重管理が再発する)。
- Elith 側の出力変更に追随できない。**すでに 1 度起きている** —
  Stage2 の `（判定区分：X）` に依存した `elith-report-highlights.ts` は、
  新形式で**無言で空になる** (§5.2)。

そこで、以下を**実装上の制約**とする。

#### 1.2.1 要望の 3 分類と、対応コスト

新しい要望が来たら、まずどれかに仕分ける。**仕分けが設計を守る。**

| 種別 | 例 | 対応 |
|---|---|---|
| **(a) 見せ方** | 章の順序・表示可否・見出し文言・既定の開閉・注意書き | **コード変更なし**。`app_config` を admin から変更 (§1.2.2) |
| **(b) 構造** | 章を追加・新しいデータ源・表の列を増やす | アダプタとレンダラの追加。既存章に影響を出さない |
| **(c) 内容の創作** | 「原因も書いて」「がんリスクも出して」「良否を判定して」 | **不可**。受領データに無いものは作らない (§6)。**断る根拠を §6 に置いてある** |

**(c) を (a)(b) のふりをして受けないこと。** 要望の圧が最も強く出るのは (c) なので、
仕様書のこの表を根拠に会話する。

#### 1.2.2 章立てを設定に出す (コードに埋めない)

章の **key / 表示名 / 出力元 / 順序 / 既定の開閉 / 印刷に載せるか** をレジストリとして持ち、
**`.astro` にハードコードしない**。

- **コード既定のレジストリ**を持ち、**`diagnosis.app_config` で上書きできる**ようにする。
  優先順位は既存の流儀どおり **DB値 → コード既定** (`src/lib/app-config.ts`)。
- 設定値の置き場所の判断基準は**秘匿性** (CLAUDE.md 確定事項)。章立て・文言は秘匿性が低く
  切り替えが想定されるので **`app_config` が正しい置き場所**。env に置かない。
- 既存の前例に倣う: `ui.support_contact` / `ui.health_age_followup`
  (`app-config.ts:33,35`)。**既定は空・空なら出さない** = 架空の文言を作らない流儀も踏襲する。
- admin UI は **wellfort-site 側**に置く (Scan-Chat-AI は API 提供側。CLAUDE.md 確定事項)。

これにより **(a) の要望は「デプロイ不要・admin から即時」** になる。反映は TTL 45 秒。

#### 1.2.3 受領形式と表示モデルを分ける

**`受領JSON → 表示モデル(ViewModel) → レンダラ`** の 3 層にし、層をまたいだ直参照を作らない。

- **Elith の形式変更はアダプタ 1 枚で吸収する。** 画面側は表示モデルしか知らない。
- Stage2 → Stage3 で実際に形式が変わった (`判定区分` と `[pN]` が消えた) 実績があるため、
  **次も変わる前提**で置く。
- 表示モデルは型を持つ (`ElithSection[]` に押し込めず、章・所見・値の構造を素直に表す)。

#### 1.2.4 変換規則は 1 箇所に集約する

受領テキストからの抽出・整形は**単一のモジュールが所有する**。`.astro` に正規表現を散らさない。

本リポジトリには既に同じ規律の前例がある —
納品整形は `elith-export.ts` の `sanitizeMeasurementsForDelivery()` に集約し、
「二重管理しない」と CLAUDE.md に明記されている。**それと同じ扱いにする。**

#### 1.2.5 画面と印刷は同じレンダラから出す

`?print=1` は**モード引数**であって別実装ではない (§3.3)。
**章を 1 つ足したら印刷ビューにも自動で載る**こと。載らない実装にしない。

#### 1.2.6 抽出できなかったことを可視化する

フォーマット依存の抽出 (§5.2) は **fail-safe (拾えなければ何も出さない)** を維持する。
ただし現状は**黙って空になる**ので、それだけでは気づけない。

→ **抽出監査を admin に出す** (どの章を認識し、何件の所見を拾い、何を拾えなかったか)。
スキャン側の `vqa_audit` と同じ流儀。**納品/表示データには混ぜない。**

#### 1.2.7 回帰を機械で担保する

本リポジトリの流儀 (🎯ゴールデン) をここにも適用する。

- 受領 JSON を fixture として置き、**表示モデルのスナップショット**を比較する。
- 担保したいのは主に **「文言を書き換えていないこと」** (要約・言い換え・並べ替えをしない
  = ミッション④)。章の並べ替えや設定変更で本文が変質していないかを機械で見る。

#### 1.2.8 紙面テンプレートに版を持たせる

紙面を変えたらテンプレート版を上げ、**紙面に印字する** (§3.7)。
端末に保存された控え (§3.6) は回収できないため、**どの版の紙かを紙自身が名乗る**必要がある。

**JSON のほうが上位**であり、入力を JSON に切り替えるのは扱いやすさだけの理由ではない。

## 3. 出力形式

| 用途 | 形式 | 方式 |
|---|---|---|
| **Web アプリでの閲覧 (正)** | **HTML** | 既存 `/report` を置き換え。Astro SSR |
| **プリントアウト / PDF 保存** | **HTML（印刷専用ビュー）** | `/report?print=1` を全展開・UI なしで出す。`@media print` は上乗せで、**それに依存しない** (§3.2〜3.3) |
| **端末に残す (オフライン)** | **ファイル保存** | 印刷専用ビュー → 共有 → PDF で「ファイル」アプリへ。**オフライン要件はこの報告書のみ** (§3.6) |
| Elith 受領 PDF | PDF | **原本として保管のみ**。既定では画面に出さない |

### 3.1 なぜ PDF を生成しないか (Phase 1)

サーバ側 PDF 生成は次のコストを伴うため、**必要が生じるまで持ち込まない**:

- Vercel Serverless で Chromium を動かす必要がある (`@sparticuz/chromium` 等)。
  関数サイズと**60 秒タイムアウト** (`system_architecture_overview.md` L316) に直接効く。
- 生成物の保管・世代管理が増える (原本 S3・10 年保管の対象になるかの判断も要る)。
- **紙面が 2 系統になる** (HTML と PDF)。片方だけ直る事故が起きる。

ただし **`@media print` だけに頼るのは不可** (次項)。

### 3.2 【重要】`@media print` だけでは iPhone で成立しない

**主要利用者は 50〜65 代の経営者・役員** (UI 原則) で、閲覧はスマートフォンが主。
iOS には**結果の異なる 2 経路**があり、見つけやすいほうが印刷 CSS を通らない。

| 経路 | `@media print` | 出力 | 発見しやすさ |
|---|---|---|---|
| 共有 → **プリント** | **効く** | 印刷用レイアウト | 低 (PDF 化は更にピンチアウトが要る) |
| 共有 → **PDF** (オプションで PDF を選択) | **効かない** | 画面 CSS のままの PDF | **高** |

後者が素通りするため、次が起きる:

- ナビ・タブ・操作 UI がそのまま紙面に載る。
- **折りたたんだ本文が PDF に載らない = 中身が欠ける。** 体裁の問題ではなく欠落。

→ **`@media print` を前提にした設計は採用しない。**

### 3.3 採用方式: 印刷専用ビュー (経路非依存)

**`/report?print=1`** を用意する。

- 全セクション**展開済み**・ナビ/タブ/操作 UI なし・本文のみを、**通常の画面 CSS として**出す。
- `@media print` も併用するが、**効かなくても同じ紙面になる**ようにする (印刷 CSS は上乗せ)。
- 導線は「印刷・PDFで保存」ボタン 1 つ。押すとこのビューへ遷移し、端末別の手順を画面に出す。

これにより **共有→プリント / 共有→PDF のどちらを選んでも同じ紙面**が得られる。
ユーザーがどちらを取るかは制御できない以上、経路非依存が唯一堅い設計。追加インフラはゼロ。

**折りたたみは `?print=1` では使わない** (畳んだ状態が出力に漏れる余地を残さない)。

### 3.4 実機で確認すること (未検証)

**開発環境に iPhone が無く、Playwright の Chromium では WebKit(iOS) を再現できない。**
以下は未確認の仮説を含むため、実機で確かめる。**印刷専用ビュー方式は結果がどちらでも
成立する**ので、この確認を待たずに設計を確定してよい。

- iOS 共有 → PDF が出す PDF のページ分割 (1 枚の長大ページか、用紙サイズで分割か)。
- iOS 共有 → プリントでの `@media print` の効き (ヘッダ/フッタ・`break-inside: avoid`)。
- Android Chrome (共有 → 印刷 → PDF に保存) での同等確認。
- 表・所見カードが紙面幅で破綻しないか。

### 3.5 PDF 生成が要るのはどんなときか (Phase 2 の条件)

いずれかが確定したら実装する。**現時点ではどれも要件になっていない。**

- **表示の証跡が要る場合**。テンプレートは今後変わるので、「その日ユーザーに見せた紙面」を
  後から再現することはできない。監査要件があるならスナップショットの保存が要る。
- メール添付・郵送など、**アプリ外へ配る**運用が決まった場合。
- 面談時に**医師へ渡す**用途が決まった場合。
- **§3.4 の実機確認で、印刷専用ビューでも埋まらない差が出た場合** (用紙サイズの制御・
  ページ番号・表紙の体裁など)。これが Phase 2 の最有力の発動条件。
- **§3.6 のファイル保存の手順が、実機で利用者に辿れないと分かった場合**。
  サーバー生成ならワンタップの「保存」で済む。A を実機で試してから判断する。

### 3.6 端末に残す (オフライン対応) — 発注者判断 2026-08-28

#### 要件と、その根拠

**オフラインで見たいのは「AI疾病予防報告書」だけ。** アプリ全体のオフライン対応は対象外。

理由 (発注者):

- **他の検査報告書は紙でユーザーの手元に届く。** 検診・人間ドック・がんリスク・遺伝子・血液は
  いずれも実物が手元に残る。
- **この報告書だけは、アプリからしか入手できない。** 紙の代替物が存在しない。
- **この報告書が本 Web アプリの肝**であり、「見たいときに見られない」が最も起きてはならない。

→ **報告書 1 点を端末に恒久的に残せること**が要件。アプリ全体をオフラインで動かすことではない。

#### 採用方式: A. ファイル (PDF) として「ファイル」アプリに保存

印刷専用ビュー (§3.3) → 共有 → PDF 形式で「ファイルに保存」。

| | |
|---|---|
| 保存先 | iOS「ファイル」アプリ (iCloud Drive / この iPhone 内)。**ブラウザのストレージの外** |
| 消えるか | **消えない。** ブラウザのデータ削除・ITP のストレージ破棄の対象外 |
| オフライン | **完全に可**。アプリを開く必要すらない |
| 二次利用 | 医師へ提示・家族へ共有・印刷、いずれも可 |
| 追加インフラ | **ゼロ**。§3.3 の印刷専用ビューをそのまま使う |

**「都度サーバーから DL したくない」に最も素直に応える。1 回保存すれば以後アプリ不要。**

#### UI 導線の要件

主要利用者は 50〜65 代。**「共有 → オプション → PDF → ファイルに保存」を自力で辿らせない。**

- 報告書画面に **「iPhone に保存する」** を独立した導線として置く (印刷と並べない・埋もれさせない)。
- 押すと印刷専用ビューへ遷移し、**端末を判定して手順を画面に出す** (iOS / Android / PC)。
- 手順はスクリーンショットではなく短い文章で。OS 更新で文言が変わるため、
  **メニュー名を断定せず「共有ボタン（□に↑）」のように形で示す**。

#### 保存した控えは「その時点のスナップショット」

Elith が報告書を再発行すると (`status='superseded'`)、端末の控えは古くなる。**回収も更新もできない。**

- 紙面に **作成日と版** を必ず印字する (§3.7 の印刷ヘッダ/フッタ要件)。
- アプリ側で新しい版を受領したら、報告書画面に「新しい報告書が届いています」を出す。
- **古い控えを消す手段は無い**前提で設計する (消せると誤解させる UI を作らない)。

#### なぜ Service Worker でキャッシュしないか

技術的には可能だが、**この要件に対しては割に合わない**:

1. **iOS のストレージ破棄の扱いが読めない。** Safari は一定期間アクセスの無いサイトの
   script-writable storage (Cache API / IndexedDB 等) を破棄する。ホーム画面に追加した
   Web アプリは対象外とされるが、**これは Apple 側の変更が続く領域で、記憶を根拠にできない**
   (R3)。採用するなら WebKit 公式で裏を取る必要がある。**「消えないはず」で設計して消えると、
   いちばん見せたいものが消える。**
2. **認証と噛み合わない。** `/report` は SSR で、サーバーがユーザーを解決している
   (`report.astro:32` `prerender = false` / `astro.config.mjs:7` `output: 'server'`)。
   オフラインで出すにはキャッシュ済み HTML を**認証を通さずに返す**しかなく、
   **端末のロックさえ解ければ他人の検査結果が読める**状態になる。
3. **実装量が大きい。** SW ライフサイクル・更新戦略・ユーザー別のキャッシュ分離・
   古い報告書を掴み続ける事故の防止。**報告書 1 点を残すだけなら A で足りる。**

#### ただし Service Worker は入れる (用途を絞って)

現状 **SW は存在しない** (`grep` ヒット 0)。一方 `manifest.webmanifest` は
`display: standalone` なので、**ホーム画面から起動すると「アプリの見た目で Safari のエラー画面」**
になる。アプリらしく見えるぶん体験としてはむしろ悪い。

→ **オフライン時に「通信がありません／保存済みの報告書はファイルアプリにあります」と案内する
だけの最小の SW を入れる。** 報告書本体はキャッシュしない (上記 1〜3 を踏まない)。

#### 実機で確認すること

- 共有シートから PDF 形式で「ファイルに保存」した紙面が、印刷専用ビューどおりか。
- 保存された PDF のページ分割 (§3.4 と同じ確認)。
- Android (Chrome → 印刷 → PDF に保存 → ファイル) での同等確認。

### 3.7 印刷 CSS の要件 (上乗せ分)

`?print=1` の画面 CSS で紙面が成立していることが前提。その上で:

- ヘッダ/フッタ (氏名・**作成日**・**版**・ページ番号) を `position: fixed` で入れる。
  端末に保存された控えが古いかどうかを、その紙だけで判別できるようにするため (§3.6)。
- 章の途中で切れないよう `break-inside: avoid` を所見カード・表に付ける。
- 背景色は `print-color-adjust: exact` を指定しない限り落ちる。**色だけで意味を伝えない**
  (アイコン＋テキスト＋色の 3 点セット。UI 原則と同じ)。
- **クライアント側 PDF 生成ライブラリ (html2pdf / jsPDF) は使わない。**
  和文フォントの埋め込みでファイルが肥大し、改ページ品質も低い。

## 5. 変換規則

**すべて決定論。LLM を通さない。** アプリは受領テキストを並べ替え・構造化するだけで、
文言を書き換えない (要約・言い換え・並べ替えをしない = ミッション④)。

### 5.1 セクションの取り込み

新形式 (dict) を既存の `ElithSection[]` (`src/lib/elith-parser.ts:10`) へ写す:

| 新形式 | 既存 |
|---|---|
| `<key>.section_name` | `section_name` |
| `<key>.actual_chars` | `char_count` |
| `<key>.text` | `text` |
| `health_age` | 別扱い (表紙) |

**`[pN]` は新形式に存在しない** (実測 0 件)。原本 PDF へのページジャンプ
(`report.astro` の `#pdf-viewer` 導線) は**成立しないので廃止する**。

### 5.2 「今回みておくこと」の抽出

`blood_analysis` の各 `【項目】` ブロックから、**Elith 自身が書いた判定文**を拾う。

- 検出語 (実測): `基準範囲を上回っています` / `基準範囲内であり` / `基準値を下回`
- 併せて、同ブロック内の `値 + （基準値：〜）` を正規表現で取り出し、値・基準値・判定を
  構造化して見出しに出す。説明文は本文として畳む。

**アプリは値と基準値を比べない。** 拾うのは Elith が明記した判定文だけ。

> **既存 `elith-report-highlights.ts` はそのままでは動かない。**
> 同ファイルは `（判定区分：X）` という Stage2 の書式に依存している (L20 `JUDGEMENT_ORDER`)。
> 新形式には `判定区分` が **0 件** (実測)。fail-safe 設計なので誤った要点は出ないが、
> **何も出なくなる**。検出ルールを上記に差し替えること。

### 5.3 検査値テーブル

- 値 = `health_checkup.json`。
- 基準値 = `blood_analysis` 本文から抽出できた 8 件のみ。**無い項目は基準値欄を空にする**
  (外部のマスタで補完しない = 捏造ゼロ)。
- **同名別値は自動採用しない** (§7)。

見本にあって受領データに無い要素。**発注者判断 (2026-08-28): 受領データに無いものは作らない。**

| ① | 要注意項目／良好な項目 | **部分的に可**。Elith の判定文がある 5 ブロックのみ。「尿検査 異常なし」等、言及外の項目に良否は付けられない |
| ② | 原理／原因／想定される疾患／悪化した場合／自覚症状 | **「原理」のみ可**。原因・病名・予後・症状は 0 件 |

### 6.1 これは欠損ではなく方針の相違

病名 0 件・「がん」0 件・原因の断定 0 件は徹底された編集方針。**見本は Elith とは別の書き手を
前提にした設計**である。当社のミッション④とも一致するので、①〜④ を埋めない判断は方針として
