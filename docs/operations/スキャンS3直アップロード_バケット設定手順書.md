# スキャン S3 直アップロード バケット設定手順書

AI スキャンで **10 MB までのファイル (とくに PDF) を通す**ために、S3 バケット
`wellfort-ai-input` に対して行う 2 つの設定。

- **① CORS** — これが無いと PDF は 3.2 MB のままになる (**本番で PDF を通すには必須**)
- **② ライフサイクル** — 一時領域に置いたファイルを自動で消す (**運用衛生・任意だが推奨**)

アプリ側の実装は完了済み。**この手順を実施した時点で有効になる** (再デプロイ不要)。

- 実装: `src/lib/scan-upload-ticket.ts` / `src/pages/api/scan/upload-ticket.ts` / `src/scripts/scan-upload.ts`
- 設計の根拠: CLAUDE.md「スキャンのアップロード上限」

> **この作業には AWS コンソール/CLI の権限が必要です。**
> AWS キーは Vercel 本番 env で一元管理する方針 (CLAUDE.md) のため、開発側では実施できません。
> Wellfort / UNFIX の AWS 管理者が実施してください。

## 0. 前提 (2026-09-04 実測)

推測ではなく、本番の口を叩いて確かめた値です。

| 項目 | 値 | 確かめ方 |
|---|---|---|
| バケット | `wellfort-ai-input` | 下記コマンドの `upload_url` のホスト名 |
| リージョン | `ap-northeast-1` | 同上 |
| 対象プレフィックス | **`scan-accuracy-test/scan-uploads/`** | 同コマンドの `key` |
| アプリのオリジン | `https://scan-chat-ai.vercel.app` | 本番 URL (将来 `https://app.wellfort.co.jp`) |
| CORS の現状 | **未設定** | §3 のプリフライトが `CORS is not enabled for this bucket` |

**プレフィックスは必ずこのコマンドで確認してから設定してください。**
`AWS_S3_PREFIX` を変更すると変わります (既定は `scan-accuracy-test/`)。
このコマンドは署名を 1 つ発行するだけで、**ファイルは作られません**。

```bash
curl -s -X POST https://scan-chat-ai.vercel.app/api/scan/upload-ticket \
  -H 'content-type: application/json' \
  -d '{"contentType":"application/pdf","bytes":8000000}'
```

返る `key` の `<UUID>.pdf` より前が、②で使うプレフィックスです。

```
"key":"scan-accuracy-test/scan-uploads/2026/09/04/1fd70e3e-....pdf"
        └─────────── これを ② に使う ───────────┘
```

## 1. ① CORS の設定 (必須)

### 1.1 なぜ要るのか

ブラウザが S3 へ直接 PUT するため。Vercel の関数を通さないので
**4.5 MB のリクエストボディ上限にかからない**、というのがこの方式の要点です。

### 1.2 ⚠ よくある誤解: CORS はバケットを公開しません

CORS は「**ブラウザが**別オリジンへの応答を JavaScript に見せてよいか」を決めるだけの仕組みです。
**アクセス権限とは別物**で、この設定でバケットが公開されることはありません。

書き込みの権限は **presigned URL (署名)** が担っており、署名にはキー・Content-Type・
サイズ・15 分の期限が焼き込まれています。**バケットポリシーやパブリックアクセスブロックは
一切変更しません** (変更しないでください)。

### 1.3 設定する JSON

```json
[
  {
    "AllowedOrigins": [
      "https://scan-chat-ai.vercel.app"
    ],
    "AllowedMethods": [
      "PUT"
    ],
    "AllowedHeaders": [
      "content-type"
    ],
    "ExposeHeaders": [],
    "MaxAgeSeconds": 3000
  }
]
```

**最小限にしてあります**。アプリがブラウザから行うのは `PUT` だけで、送るヘッダは
`content-type` だけです (署名に固定されているため、他のヘッダを付けると S3 が拒否します)。
`GET` は入れません — サーバ側の読み出しは SigV4 で行われ、CORS を通らないためです。

書式の出典: AWS 公式
[Elements of a CORS configuration](https://docs.aws.amazon.com/AmazonS3/latest/userguide/ManageCorsUsing.html)
(コンソールは **JSON のみ**受け付けます)。

#### 将来 `app.wellfort.co.jp` へ移すとき

`AllowedOrigins` に足すだけです (**移行後に消し忘れないよう、切替時に旧オリジンを外す**)。

```json
"AllowedOrigins": [
  "https://scan-chat-ai.vercel.app",
  "https://app.wellfort.co.jp"
]
```

#### Vercel のプレビュー環境も通したい場合 (任意・非推奨)

プレビューは `scan-chat-ai-<ハッシュ>-<チーム>.vercel.app` のように URL が毎回変わるため、
個別指定できません。どうしても必要なら `"https://*.vercel.app"` を足せます
(AllowedOrigins の `*` は **1 つだけ**使えます・出典は上記公式)。
ただし **Vercel 上の第三者のサイトまでオリジンとして許すことになる**ので、
**既定では入れないでください**。プレビューでの検証は、その都度そのオリジンを
一時的に足して、終わったら外す運用を推奨します。

### 1.4 手順 — マネジメントコンソール

1. S3 コンソール → バケット **`wellfort-ai-input`** を開く
2. **「アクセス許可」** タブ
3. 一番下の **「Cross-Origin Resource Sharing (CORS)」** → **「編集」**
4. 上の JSON を貼り付けて **「変更の保存」**

> **既に CORS が入っていた場合は上書きしないでください。** 配列に要素を 1 つ**追加**します
> (CORS 設定はバケットに 1 つで、ルールを最大 100 個持てます)。今回は実測で未設定でした。

### 1.5 手順 — AWS CLI

```bash
cat > /tmp/scan-cors.json <<'JSON'
{
  "CORSRules": [
    {
      "AllowedOrigins": ["https://scan-chat-ai.vercel.app"],
      "AllowedMethods": ["PUT"],
      "AllowedHeaders": ["content-type"],
      "ExposeHeaders": [],
      "MaxAgeSeconds": 3000
    }
  ]
}
JSON

# 既存の設定を必ず先に確認する (NoSuchCORSConfiguration なら未設定)
aws s3api get-bucket-cors --bucket wellfort-ai-input --region ap-northeast-1

aws s3api put-bucket-cors --bucket wellfort-ai-input --region ap-northeast-1 \
  --cors-configuration file:///tmp/scan-cors.json
```

## 2. ② ライフサイクルの設定 (推奨)

### 2.1 なぜ要るのか

`scan-uploads/` は **解析のために数秒だけ置く一時領域**です。放置すると
利用者がスキャンするたびに検査票の画像・PDF が溜まり続けます。

**原本の保管とは別物です** — 原本の 10 年保管は `originals-storage.ts` が
別バケット (`AWS_S3_ORIGINALS_BUCKET`) で担当します
(`docs/operations/S3原本ストレージ_構築手順書.md`)。ここは消してよい領域です。

### 2.2 ⚠ 先に確認すること 2 つ

**(a) バージョニングが有効か**

有効な場合、`Expiration` は**削除マーカーを付けるだけで実データは残ります**
(出典: AWS 公式
[Examples of S3 Lifecycle configurations](https://docs.aws.amazon.com/AmazonS3/latest/userguide/lifecycle-configuration-examples.html)
「Specifying a lifecycle rule for a versioning-enabled bucket」)。
その場合は `NoncurrentVersionExpiration` も足す必要があります (§2.3 の B)。

```bash
aws s3api get-bucket-versioning --bucket wellfort-ai-input --region ap-northeast-1
# 何も返らない = 未設定 → A を使う
# "Status": "Enabled"   → B を使う
```

**(b) Object Lock が掛かっていないか**

掛かっていると保持期間中は**ライフサイクルでも消せません**。

```bash
aws s3api get-object-lock-configuration --bucket wellfort-ai-input --region ap-northeast-1
# ObjectLockConfigurationNotFoundError なら掛かっていない (想定どおり)
```

掛かっていた場合は、**この手順を進めずに一度ご相談ください** (Elith 納品バケットに
Object Lock が掛かっているなら、それ自体が別途確認すべき事項です)。

### 2.3 設定する JSON

**A. バージョニング無効の場合 (通常はこちら)**

```json
{
  "Rules": [
    {
      "ID": "expire-scan-uploads",
      "Filter": { "Prefix": "scan-accuracy-test/scan-uploads/" },
      "Status": "Enabled",
      "Expiration": { "Days": 1 },
      "AbortIncompleteMultipartUpload": { "DaysAfterInitiation": 1 }
    }
  ]
}
```

- **`Days: 1` が最短**です。ファイルは数秒で読み終わるので 1 日で十分です。
  S3 は有効期限を UTC の深夜に丸めてから削除するので、**実際には 1 日きっかりではなく
  1〜2 日ほど残ります**（作成が深夜直前だと長め）。一時領域なので問題ありません。
- `AbortIncompleteMultipartUpload` は保険です。アプリの PUT は単一パートなので通常は発生しません。

**B. バージョニングが有効な場合**

```json
{
  "Rules": [
    {
      "ID": "expire-scan-uploads",
      "Filter": { "Prefix": "scan-accuracy-test/scan-uploads/" },
      "Status": "Enabled",
      "Expiration": { "Days": 1 },
      "NoncurrentVersionExpiration": { "NoncurrentDays": 1 },
      "AbortIncompleteMultipartUpload": { "DaysAfterInitiation": 1 }
    }
  ]
}
```

`Expiration.Days` と `ExpiredObjectDeleteMarker` は**同じルールに併記できません**
(公式の注記)。`Days` を指定していれば、期限を過ぎた削除マーカーは S3 が自動で片づけます。

> **`Filter.Prefix` は §0 のコマンドで実際に返ってきた値**にしてください。
> ここを間違えると、**消してはいけない Elith 納品 JSON まで対象になります**。
> `scan-uploads/` を必ず含め、`scan-accuracy-test/` だけにしないこと。

### 2.4 手順 — マネジメントコンソール

1. S3 コンソール → バケット **`wellfort-ai-input`** → **「管理」** タブ
2. **「ライフサイクルルール」** → **「ライフサイクルルールを作成する」**
3. ルール名 `expire-scan-uploads`
4. スコープ = **「1 つ以上のフィルターを使用してこのルールのスコープを制限する」**
   → プレフィックスに **`scan-accuracy-test/scan-uploads/`**
5. アクション:
   - 「オブジェクトの現行バージョンを有効期限切れにする」→ **1 日**
   - (バージョニング有効なら)「非現行バージョンを完全に削除」→ **1 日**
   - 「未完了のマルチパートアップロードを削除」→ **1 日**
6. **確認画面でプレフィックスをもう一度読む** → 作成

### 2.5 手順 — AWS CLI

```bash
cat > /tmp/scan-lifecycle.json <<'JSON'
{
  "Rules": [
    {
      "ID": "expire-scan-uploads",
      "Filter": { "Prefix": "scan-accuracy-test/scan-uploads/" },
      "Status": "Enabled",
      "Expiration": { "Days": 1 },
      "AbortIncompleteMultipartUpload": { "DaysAfterInitiation": 1 }
    }
  ]
}
JSON

# 既存ルールを必ず先に退避する (put は全置換で、既存ルールが消えます)
aws s3api get-bucket-lifecycle-configuration --bucket wellfort-ai-input \
  --region ap-northeast-1 > /tmp/lifecycle-before.json

aws s3api put-bucket-lifecycle-configuration --bucket wellfort-ai-input \
  --region ap-northeast-1 --lifecycle-configuration file:///tmp/scan-lifecycle.json
```

> **`put-bucket-lifecycle-configuration` は全置換です。** 既存ルールがある場合は
> `/tmp/lifecycle-before.json` の `Rules` に今回のルールを足した JSON を作って投入してください。

## 3. 設定できたかの確認

### 3.1 CORS — コマンドで判定 (1 行)

**設定の前後で同じコマンドを打てば、効いたかどうかが分かります。**

```bash
curl -s -o /dev/null -w '%{http_code}\n' -X OPTIONS \
  "https://wellfort-ai-input.s3.ap-northeast-1.amazonaws.com/scan-accuracy-test/scan-uploads/test" \
  -H "Origin: https://scan-chat-ai.vercel.app" \
  -H "Access-Control-Request-Method: PUT" \
  -H "Access-Control-Request-Headers: content-type"
```

| 結果 | 意味 |
|---|---|
| **`403`** | **未設定**。本文に `CORS is not enabled for this bucket` ← **設定前の実測値** |
| **`200`** | **設定できている** |

`-i` を付けて本文とヘッダも見てください。**`access-control-allow-origin` が
返っていれば確実**です。

- 未設定時の応答は `<ResourceType>BUCKET</ResourceType>` を含んでおり、
  プリフライトが**バケット単位**で処理されていることが分かるので、
  URL 末尾のオブジェクトは存在しなくて構いません (**テスト用ファイルは不要**)。
- ただし **`200` が返ることまでは未実測**です (CORS 未設定の状態でしか試せないため)。
  もし `403` 以外の見慣れない応答が返ったら、`-i` のヘッダを添えて開発側へ連絡してください。

### 3.2 ライフサイクル

```bash
aws s3api get-bucket-lifecycle-configuration --bucket wellfort-ai-input --region ap-northeast-1
```

`expire-scan-uploads` が `"Status": "Enabled"` で返り、`Prefix` が
`scan-accuracy-test/scan-uploads/` であること。

### 3.3 アプリで実地確認 (これが最終確認)

1. スマートフォンかPCで `https://scan-chat-ai.vercel.app/scan` を開く
2. **4 MB を超える PDF** をアップロードする (**PDF であることが重要** — 画像は
   CORS が無くても圧縮経路で通ってしまうため、判定になりません)
3. 解析が始まれば成功

失敗するときは「PDF は 3.2 MB までしか送信できません」と表示されます。
これは **S3 経由が使えなかった**ことを意味します (§4 へ)。

## 4. うまくいかないときの切り分け

| 症状 | 原因の候補 | 確認 |
|---|---|---|
| PDF で「3.2 MB までしか送信できません」 | CORS 未設定 / オリジン不一致 | §3.1 が `403` か。`Origin` を実際のURLと一致させたか |
| §3.1 が `403` のまま | 別のオリジンを書いた / 保存し忘れ | `aws s3api get-bucket-cors` で現物を見る |
| 画像は通るが PDF だけ落ちる | **まさに CORS 未設定の症状** | 画像は圧縮フォールバックで通るため。§3.1 を実施 |
| チケット取得が `s3_not_configured` | Vercel の `AWS_REGION` 等が未設定 | §0 のコマンドで `ok:false` が返る |
| PUT が `403 SignatureDoesNotMatch` | 署名条件のずれ | 開発側へ連絡 (`content-type`/サイズを署名に固定しているため) |

**アプリ側は失敗しても画像なら圧縮経路へ自動で落ちます** (利用者は行き止まりになりません)。
そのぶん **CORS が効いていないことに気づきにくい**ので、§3.1 で明示的に確認してください。

---

## 5. やらないこと

- **バケットを公開しない** — パブリックアクセスブロックは触りません
- **バケットポリシーを変更しない** — 書き込み権限は presigned URL が担っています
- **`GET` を CORS に足さない** — サーバ側の読み出しは CORS を通りません
- **ライフサイクルの prefix を `scan-accuracy-test/` だけにしない** — Elith 納品 JSON が消えます
