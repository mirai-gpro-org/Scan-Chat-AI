# デモ用アカウント 仕様書

**確定: 2026-08-30・発注者指示 / 実装済み・本番稼働中**

**適用範囲はアプリ全体**（ダッシュボード / お知らせ / 検査結果 / 推移グラフ / AI疾病予防報告書）。
特定の機能の仕様ではないので、**この文書が正本**。
`docs/elith/AI疾病予防報告書_仕様書.md` §4.6 はここを指すだけ。

## 1. 目的 — 何のためにダミーを見せるのか

| | |
|---|---|
| **UI デザインの確認** | 実データが無い段階でも画面の完成形を見る |
| **機能確認** | 推移グラフ（2 回目の検査から）・過去データの切替など、材料が要る機能を通す |
| **ビジネスパートナーへのお披露目・PR** | 商談・宣伝の場でサービスの実物を見せる |

**権限の確認ではない。** だから**権限の仕組み（admin）に乗せない。**
**PR 用のアカウントは社外に渡る**ので、管理者と同じ枠に置くことはできない。
これがこの文書の中心。

---

## 2. 誰が見るか

| 閲覧者 | ダミー | 実データ |
|---|---|---|
| **デモ用アカウント**（uid が一覧にある） | **出す** | — |
| Google 認証済みの一般顧客 | **出さない** | **本人のぶんだけ** |
| **管理者（admin）** | **出さない**（uid を登録すれば出る） | 出す |
| 未サインイン | 出さない | 出さない |

**admin であることはデモの資格にならない。** 管理者を増やしてもダミーの閲覧者は増えない。
管理者がダミーを見たいなら、**その人をデモ用アカウントとして登録する**（§5・30 秒）。

**サインインは全員が通常どおり Google 認証を通る。** デモ用アカウントは
「素性の分かっている実在の Google アカウント」であって、**認証の抜け道ではない**。
認証をスキップする仕組み・共有パスワード・URL パラメータでの入場は**作らない**。

**だから登録も Google アカウントで行う**（§5）。記者やパートナーに UUID は聞けない。
相手のメールアドレスを聞いて登録し、本人がサインインした時点でダミーが出る。

### なぜ完全に分けるのか

**PR 用のアカウントは社外に渡る。** 管理者と同じ枠に置いた瞬間、
「デモを見せる」ことと「管理権限を渡す」ことが区別できなくなる。

分離の帰結として、次が構造的に保証される。

| | |
|---|---|
| デモ用アカウントは管理画面に入れない | admin の正は Wellfort 側 `admin_users`。そこに載せない |
| デモ用アカウントは `?u=` で他人を覗けない | 代理表示は `viewer.isAdmin` が要る（`viewer.ts:229`） |
| デモを増やしても権限は 1 ミリも増えない | 供給元が別（§4） |
| admin 判定が壊れてもデモは動く | デモの経路に外部依存が無い |

## 3. 判定 — uid だけ

**登録はメールアドレス、判定は uid**（§5）。ここは判定の話。

実装は `src/lib/demo-accounts.ts` の `isDemoAccount(uid)`。**同期・外部依存なし。**
`demo-data.ts` の `demoFallbackEnabled(uid)` はこれに委譲するだけ。

```
① env PUBLIC_DEMO_FALLBACK === 'false' なら false   ← 唯一の全停止スイッチ
② uid がデモ用アカウントの一覧にあるか              ← これだけ
```

**`viewerIsAdmin` のような引数は持たない。** 任意引数にすると渡し忘れても型で落ちず、
静かに挙動が変わる。**引数を無くすことで穴を構造的に消してある。**

### 代理表示（`?u=`）

`?u=` は admin だけの機能（`viewer.ts:229`）。判定に渡る uid は**表示中の相手**になるので、

- 相手がデモ用アカウント → ダミーが出る
- 相手が一般顧客 → **相手の実データが出る**（正しい挙動）

呼び出し側で場合分けする必要は無い。実測 2026-08-30（ローカル・署名 Cookie で admin として描画）:
本人（登録済）`rp-h3`=45 / `?u=` 登録済 **45** / `?u=` 未登録 **3**（`emptyVM`）。

### 責務の分界

| ファイル | 持つもの |
|---|---|
| `demo-accounts.ts` | **誰に見せるか**（資格・供給元・監査） |
| `demo-data.ts` | **何を見せるか**（ダミーデータ本体） |

混ぜていたために「admin なら見せる」という**権限の話がデータ層に紛れ込んだ**（2026-08-30）。

## 4. デモ用アカウントの一覧 = 3 つの供給元の**和**

| 供給元 | 反映 | 用途 |
|---|---|---|
| `BUILTIN_DEMO_UIDS`（`demo-accounts.ts`） | 要デプロイ | **消えない下限**。ローンチ前の確認に必ず要るぶんだけ |
| env `DEMO_ALLOWED_UIDS`（カンマ/空白/改行 区切り） | 要デプロイ | DB 障害に影響されない |
| app_config `demo.account_uids` | **即時**（TTL 45 秒） | **admin から増減**。お披露目で当日足す |

もう 1 つ app_config `demo.account_emails` があるが、これは**供給元ではなく「予約」**。
本人がサインインするまで uid が分からないので判定には効かず、
サインイン時に `demo.account_uids` へ写って初めて効く（§5）。

### 引き算が 1 段ある — 除外リスト（`demo.account_denied_uids`）

```
出す uid = ( 組み込み ∪ env ∪ app_config ) − 除外リスト
```

**発注者指示 2026-08-30「削除のできるようにして」への対応。**
組み込みと env は供給元を画面から書き換えられない（コード / Vercel env なので）。
そのままだと**外せない行が残る**。供給元を消すのではなく**引き算を 1 段足した**ので、

- どの行でも画面から外せる（「外す」）
- **「戻す」で元に戻る**（供給元は残っているので、コードや env を触らなくてよい）

**引き算は和のあと。** 順番を逆にすると、除外した uid を app_config 側で足し直せてしまう。

`§4 冒頭の「足せるが消せない方が事故が軽い」は、供給元どうしが上書きし合わないという意味`
であって、**operator が意図して外すことを禁じるものではない**。
明示的な除外は画面に「除外中」と出るので、黙って消えることにはならない。

### なぜ「上書き」でなく「和」か

上書きにすると、**admin で 1 件登録した瞬間に組み込みと env が消え**、
それまで見えていた画面が黙って空になる。**足せるが消せない**方が事故が軽い。

**全部止める手段は env `PUBLIC_DEMO_FALLBACK=false` だけ。** これが唯一の停止スイッチ。

### 組み込みを名簿として育てないこと

`BUILTIN_DEMO_UIDS` は「デプロイ無しでは消えない最小限」であって、名簿ではない。
ここに書き足す運用にすると、**アカウント 1 件ごとにデプロイが要る形に戻る**。
増えるぶんは app_config か env を使う。

**一般顧客の uid をここに書かない。** 常設になり、外すのに再デプロイが要る。

### 現在の組み込み（4 件・すべて実顧客ではない）

| uid | 何 |
|---|---|
| `d0000001-…` | テストフェーズの標準デモ（真鍋）。`supabase/seed.sql` の投入先・`DEFAULT_USER` |
| `da000001-…` | OEM 相手先ブランド向けデモ（山田太郎）。`supabase/demo_oem_account.sql` |
| `14410d5a-…` | 社内の確認用（2026-08-30 登録） |
| `186151f8-…` | 社内の確認用（2026-08-30 登録） |

後ろ 2 件を組み込みに置いたのは、**9/1 ローンチ前の確認に必ず要るので、
admin 判定や DB の状態に左右されない下限に置く**ため。

## 5. アカウントの増やし方 — admin の専用メニュー

**Wellfort 管理画面 → サイドバー「設定」→ 🎬 デモ用アカウント**（`/admin/demo-accounts`）

**管理者管理（`/admin/users`）とは別メニュー。** 同じ枠に置くと
「デモを見せる」と「管理権限を渡す」が区別できなくなる（§2）。

### 登録するのは Google アカウント（メールアドレス）

**人が扱えるのはメールアドレスだけ。**（発注者指摘 2026-08-30）

> 「マスコミ対応で、記者にデモ画面を見てもらう場合、どうするの？
> このシステムの肝は Google 認証なので、デモを見せたい人間の Google アカウントを
> 尋ねて、それを登録する方法以外ある？？」

当初は `diagnostic_user_id`（UUID）を人が入力する設計にしていた。これは
**記者やパートナーに「サインインしてデバッグ欄の UUID を送ってください」と頼む**
形になり、運用として成立しない。**uid は機械の識別子で、人は自分の uid を知らない。**

#### 手順

1. 相手の **Google アカウント（メールアドレス）**を聞く
2. 管理画面に入力し、**用途のメモ**（例: `○○新聞 取材 2026-09`）を添えて「登録する」
3. 相手がそのアカウントでサインインした時点でダミーが出る（**事前登録でよい**）

#### 初期値は管理者リストから入れる（発注者指示 2026-08-30）

一覧が空のままだと「誰も見られない」状態で始まってしまうので、
**この画面を最初に開いたとき、管理者リスト（`admin_users` の `is_active`）のメンバーを
1 度だけ自動登録する。** 手動でやり直すボタン「管理者リストから登録」もある
（管理者を追加したあとに反映したいとき）。

| | |
|---|---|
| **1 度だけ** | 目印 `demo.seeded_from_admins` が入ったら二度と自動では走らない |
| **なぜ 1 度だけか** | 毎回走らせると、**画面から外した人が次のアクセスで黙って戻る**（「外す」が効かなくなる） |
| **「一覧が空なら」を条件にしない** | 全員を外した状態が同じ理由で復活してしまう |
| 登録後は普通の行 | **1 件ずつ外せる**。組み込みのように固定されない |
| メモ | `管理者リストから登録` の固定文言。**氏名は入れない**（PII） |

**これは「admin であることが資格になる」という意味ではない。**
資格はあくまで登録された一覧だけで決まる（§2）。
これは**名簿を一度写して初期値にする操作**であって、継続的な同期ではない。
だから**このあと管理者を増やしてもダミーの閲覧者は増えない**。

管理者名簿は Wellfort 側 `admin_users` にしかない（PII）。
**引くのは admin 画面（wellfort-site）で、Scan-Chat-AI には名簿を渡さない** —
渡すのは他の登録と同じくメールアドレスで、受け口で即ハッシュになる。

メモは任意だが、PR で増えていくと後から「誰用か」が分からなくなるので推奨。
**氏名などの PII は書かない**（用途が分かる短い語で足りる）。

#### なぜ「メールで登録」なのに「判定は uid」のままなのか

| | |
|---|---|
| **登録**（人が年に数回やる） | メールアドレス。人が知っている唯一の識別子 |
| **判定**（全ページ・全リクエスト） | uid。同期・外部依存ゼロを崩さない |

判定にメールを持ち込むと、ハッシュ計算が `async` なので **§6 の「同期関数のまま」が崩れ、
~30 箇所の呼び出し側が全部 `await` になる**。TTL 内のキャッシュだけで済んでいた判定が
DB 依存にもなる。**登録の都合で判定の性質を変えない。**

橋渡しは `linkDemoEmail()`（`demo-accounts.ts`）。**サインインの経路
（`api/auth/resolve.ts`）で 1 回だけ**呼ぶ — サーバで検証済みの email と解決済みの uid が
同時に存在するのはここだけだから。突き合わせが成立したら uid を一覧へ写す。
以後は uid だけで判定できる。

**クライアントの申告した email で登録できてはいけない**（誰でもデモを有効化できてしまう）。
だから登録の突き合わせは「サインイン処理の中」以外に置かない。

**サインインは全員が通る経路なので、ここで DB 往復を増やさない。**
`linkDemoEmail` は `refreshConfig()`（TTL 尊重）だけを呼び、**`refreshConfig(true)` は呼ばない** —
強制にすると**登録の無い人＝ほぼ全員のサインインごとに DB 往復が 1 回増える**。
登録直後の反映が最大 45 秒遅れるが、これは他の app_config と同じ約束。
（実装時に一度 `refreshConfig(true)` にしていた。検査で固定してある。）

#### 案内する URL — マイページを経由しない

```
https://scan-chat-ai.vercel.app/
```

`/` は `/dashboard` へ転送される。**マイページ（`www.wellfort.co.jp/mypage`）を通す必要は無い。**
マイページのリンクは `?u=<diagnostic_user_id>` を付けるが、
**`?u=` は admin 専用**（`viewer.ts:229`）なので、デモ用アカウントに渡す URL には**付けない**。
サインインすると HttpOnly Cookie で本人が決まるので、素の URL で足りる。

将来 `app.wellfort.co.jp` に載せ替える予定（`docs/architecture/wellfort_mypage_button_spec.md`）。

#### EC の顧客でない人（記者・パートナー）を通す

**記者は Wellfort の顧客ではない**ので `resolve-customer` では引けない。
実測 2026-08-31: そのままだと `api/auth/resolve.ts` の未連携の early return に落ち、
**「お客様情報が見つかりませんでした。検査のお申し込み状況をご確認のうえ…」で入口で弾かれる**
（デモ登録が何の役にも立たない）。

→ **デモ用として登録されている人にだけ**、デモ専用の `diagnostic_user_id` を与えて中へ通す
（`resolveDemoUidByEmail`）。**未連携の early return より前**に置くこと（後ろだと到達しない）。

| | |
|---|---|
| **登録の無い人は素通り** | 従来どおり未連携。ここが緩むと誰でも入れてしまう |
| **1 度決めた uid は変わらない** | メール行に記録して使い回す。毎回変わると `app_users` に行が増え続け、履歴も繋がらない |
| **顧客レコードは作らない** | 作るのは診断側の識別子だけ。**氏名・住所などの PII は生まれない**（それらは Wellfort 側にしかない） |
| ダミーは uid に依らない | `demo-data.ts` は固定の見本なので、新しい uid でも中身は同じ |

#### メールアドレスの現物は保存しない

PII は Wellfort 側にしか置かない取り決めがあり、`diagnosis` スキーマには置けない。
保存するのは次の 4 つだけで、**現物からは一方向・現物へは戻せない**。

| 保存するもの | 例 |
|---|---|
| sha256 | `9f86d0…`（照合に使う。大文字と前後の空白だけ吸収） |
| 表示用マスク | `r*******@example.com`（admin が「誰の行か」を見分けるため） |
| uid | サインイン後に判明した `diagnostic_user_id`。**それまでは `-`** |
| 用途のメモ | `○○新聞 取材 2026-09` |

保存形式は app_config `demo.account_emails` に **1 行 1 件**:
`<sha256> <マスク> <uid|->  # メモ`

現物のアドレスが通るのは **wellfort-site の中継 → Scan-Chat-AI の受け口**までで、
受け取った直後にハッシュへ変換する。**中継でもログに出さない。**

### 画面が見せるもの

**上段＝人が使うところ（Google アカウント）**

| | |
|---|---|
| 一覧 | マスクしたアドレス / メモ / **状態** / 外す |
| 状態 | `✅ サインイン済み・表示中` か `サインイン待ち（本人が入ると表示されます）` |
| 全停止の警告 | `PUBLIC_DEMO_FALLBACK=false` のとき、**一覧に関わらず出ない**旨を最初に出す |

**「サインイン待ち」を異常に見せないこと。** 登録しただけの状態は正常で、
これを出さないと「登録したのに一覧に uid が無い」を不具合と誤解する。

全停止の警告が要る理由: それが入っていることに気づかないと、
登録したのに出ない状態を延々追うことになる。

**下段＝詳細（`<details>` で畳んである）**

uid を直接あつかう。**すでにサインイン済みの人をすぐ登録したい**ときと、
登録の実体を確認したいときのためのもので、通常は開かない。
一覧には uid / メモ / **登録元**（この画面 / 組み込み / 環境変数）が出る。

**どの行にも「外す」が出る。** ただし外し方が 2 通りあり、画面は使い分ける。

| 行 | 押したときの動作 |
|---|---|
| この画面で足した uid | 消す（`remove`） |
| 組み込み / env / メール登録から来た行 | **除外リストに入れる**（`deny`）。行は「除外中」で残り、**「戻す」で復帰** |

供給元（コード / Vercel env / メール登録）を書き換えられないものは、消すのではなく止める。
消したように見せて実は消えていない、という状態を作らないためにこうしてある。

### 拒否される操作と、そのときの表示

| 操作 | 表示される理由 |
|---|---|
| メールアドレスの形式が違う | `メールアドレスの形式が違う` |
| uid の形式が違う | `uid の形式が違う` |
| 組み込み / env に既にある uid を追加 | `組み込み / env に既に登録されている (追加不要)` |
| 組み込み / env を `remove` で外そうとする | `組み込み / env は除外リストで止める (画面の「外す」がそうする)` |
| すでに除外している uid を外そうとする | `すでに除外されている` |
| 除外していない uid を戻そうとする | `除外リストに無い` |
| **メール登録から来た uid を uid 側で外そうとする** | `メール登録 (r***@…) から来ているので、そちらを外してください` |
| 登録されていない | `登録されていない` |

**メールアドレスの実在確認はしない。** できないし、間違っていても実害は「デモが出ない」だけ。

**メール登録由来の uid を uid 側から外させないのが要点。** 外しても
次のサインインで `linkDemoEmail` が同じ uid を書き直すため、
**外したつもりが数分後に復活する＝黙って効かない操作**になる。
画面でも「メール登録」と出して「外す」を消してある。

**逆にメール行を外すときは uid 側も一緒に外す。** メールだけ外して uid が残ると、
画面上は外れたように見えて**実際には本人にデモが出続ける**（一番まずい形）。

**中身が変わらないリクエストでは保存しない。** 全件が却下されたときに保存へ行くと、
**保存の失敗が返って却下理由が見えなくなる**（実装時に踏んだ・実測で確認）。

### 経路（UI と処理の分界）

```
/admin/demo-accounts (wellfort-site・画面)
   ↓ ユーザーのアクセストークン + anon apikey で admin_users を照会
/api/admin/demo-accounts (wellfort-site・中継)     ← 現物のアドレスが通る唯一の場所
   ↓ Bearer SCAN_CHAT_AI_API_KEY
/api/admin/demo-accounts (Scan-Chat-AI・処理)      ← ここで sha256 + マスクへ変換
   ↓
app_config `demo.account_emails`（予約）

── 本人がサインイン ──
/api/auth/resolve (Scan-Chat-AI)
   ↓ linkDemoEmail(検証済み email, 解決済み uid)
app_config `demo.account_uids`（以後の判定はこちらだけ）
```

**Scan-Chat-AI に admin 画面は作らない**（CLAUDE.md の分界）。
汎用の運用パラメータ画面（Elith バッチ → ⚙ 運用パラメータ）からも同じキーを編集できるが、
**通常はこの専用メニューを使う**（1 件ずつ安全に足せる・状態が見える・却下理由が出る）。

### 減らし方

専用メニューの「外す」。**どの行でも外せる**（§4 の除外リスト）。
メール行を外せば uid も一緒に外れる。組み込み / env は「除外中」になり、**「戻す」で復帰**。
臨時に全部止めるなら `PUBLIC_DEMO_FALLBACK=false`。

## 6. 実装上の約束

| | |
|---|---|
| **資格は `demo-accounts.ts` だけが決める** | 「誰に見せるか」を他所へ書かない。混ぜると権限の話がデータ層に紛れ込む |
| **引数は uid 1 つ** | 任意の第 2 引数を足さない。渡し忘れても型で落ちず、静かに挙動が変わる |
| **admin を参照しない** | デモの経路（入口 4 モジュール + ページ 5 枚）に `isAdmin` を出さない |
| **同期関数のまま** | ~30 箇所から呼ばれる。async にすると全経路の書き換えになり、「DB が引けないと黙ってデモが消える」依存も増える |
| **`demoAccountUids()` はキャッシュしない** | `cfg()` は TTL 45 秒で入れ替わる。固定すると admin 画面からの登録が反映されない |
| **`refreshConfig()` はデータ取得より前** | 後ろだと初回リクエストで登録が効かず、コード既定に落ちる（5 ページとも） |
| **uid 未指定は false** | fail-safe をこちらへ倒す。誤ってダミーが出るより空表示の方が安全 |
| **メールは登録の入口だけ** | 判定（`isDemoAccount`）に email を持ち込まない。持ち込むと同期でなくなる（§5） |
| **メールの現物を保存しない** | sha256 / マスク / uid / メモ の 4 つだけ。PII は Wellfort 側にしか置かない |
| **突き合わせはサインインの中だけ** | 検証済み email と uid が同時にあるのは `api/auth/resolve.ts` だけ。申告された email で登録できてはいけない |
| **サインイン済みかは「記録」で見る** | ラベルの一致で推測しない。ラベルは admin が書き換えられるので**黙って誤判定する**（実装時に一度そうなっていた） |
| **除外は和のあと** | 順番を逆にすると、除外した uid を app_config 側で足し直せてしまう |
| **管理者リストからの登録は 1 度だけ** | 繰り返すと外した人が黙って戻り、「外す」が効かなくなる。目印は上書きしない |

## 7. 検証 `npm run verify:demo-gate`

規則を**実装と独立に書き下して**突き合わせる（14 ケース）＋
**メール登録・除外リスト・記者の導線の実挙動を実際に動かして**確かめる（32 件）。`npm run verify:report` に同梱。

見ているもの:

- 14 ケースの真偽（デモ用アカウント / PR 登録 / admin / 一般顧客 / 未サインイン / **メール登録の前後** × env × 代理表示）
- **デモの経路に admin が現れないこと**（入口 4 モジュール + ページ 5 枚 + `demoOk` の復活）
- **引数が uid 1 つであること**（admin を受け取る形に戻すと落ちる）
- 供給元 3 つが**和**として生きていること・キャッシュしていないこと
- 資格が `demo-accounts.ts` に一本化されていること（`demo-data.ts` が一覧を持たない）
- **`?u=` の代理表示が admin 限定のままであること**（社外に渡すアカウントが他人を覗けない）
- `app_config` にキーがあること・5 ページが `refreshConfig()` を先に呼ぶこと
- admin 判定にベタ書き名簿を持ち込んでいないこと（別件だが同じ轍なので見張る）

**「admin だが uid 未登録 → 出さない」を明示的に固定してある。**
ここが true に戻ると、管理者を増やすたびにダミーの閲覧者が増える形に逆戻りする。

### メール登録は「書いてあるか」でなく「動くか」を見る

§1〜6 の検査は**テキストを読むだけ**で、動かしていない。メール登録は
`demo-accounts.ts` の実物を transpile して呼び、app_config だけ差し替えて
（DB を触らずに値の出入りを握って）実際に動かす。

とくに固定してあるのは:

- **保存物のどこにも現物のアドレスが出てこないこと** — 目視では抜けるし、抜けても画面は正常に見える
- 大文字・空白の違いを吸収して同じ人と分かること
- サインイン前は `-`、サインイン後に uid が入り、**その場でデモ対象になる**こと
- **登録の無い人のサインインで書き込みに行かないこと**（全ユーザーが通る経路なので）
- 2 回目以降のサインインで書き込みが増えないこと
- **ラベルを書き換えても「サインイン済み」を誤らないこと**
- **組み込みでも除外でき、戻せば元どおりになること**（供給元を消していない）
- **除外が和のあとに効くこと**（app_config で足し直しても復活しない）
- 管理者リストからの自動登録が**目印を見ていること**（毎回走ると「外す」が効かなくなる）
- **EC の顧客でない人に uid を与える処理が、未連携の early return より前にあること**
  （後ろだと到達せず、記者は入口で弾かれる）
- 登録の無い人には uid を与えないこと・**2 回目のサインインで uid が変わらないこと**

退行を注入して**実際に落ちること**を確認済み。
`hashEmail` が現物を返すよう壊すと 12 件、除外を和の前に動かすと 4 件、
記者の導線を early return の後ろへ動かすと 1 件が落ちる。
**緑であることは正しさの証明にならない** — 落ちることを確かめて初めて検査になる。

### ここは静かに壊れる

失敗の出方は 2 つで、**どちらも画面を見ただけでは気づけない**。

1. デモ用アカウントで画面が空になる → **お披露目の当日に気づく**
2. 実顧客に他人名義のダミーが「自分の結果」として出る → **気づかれないまま流出する**

だから規則を表で固定する。**実装を読んで期待値を書かない**（「実装が実装どおり」を確認するだけになる）。

## 8. 切り分け

```
GET https://scan-chat-ai.vercel.app/api/debug/viewer?k=<PROBE_UPLOAD_TOKEN>
```

| 出力 | 意味 |
|---|---|
| `report.demo_enabled: false` | デモが出ていない → uid を登録する |
| `report.effective_uid` | **画面が実際に使っている uid**（Cookie の uid とは限らない） |
| `viewer.is_admin` ≠ `edge.is_admin` | `warning` に出る。Cookie が古い＝期限切れで admin を失う |
| `edge.admin_lookup` | `readable` / `active_count` / `matched` で admin 照会の失敗と不在を区別 |

**`?u=` が付いていないか必ず確認する。** 代理表示中は相手の uid で判定されるので、
相手がデモ用アカウントでなければ空になる。**2026-08-30 にこれで 2 時間溶かした。**

`PROBE_UPLOAD_TOKEN` は使い捨ての運用トークン。**リポジトリに置かない**。
用が済んだら Vercel の env ごと削除してよい（削除すると診断は 503 になる）。
