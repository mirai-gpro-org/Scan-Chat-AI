**確定: 2026-08-30・発注者指示 / 実装済み・本番稼働中**

**適用範囲はアプリ全体**（ダッシュボード / お知らせ / 検査結果 / 推移グラフ / AI疾病予防報告書）。
特定の機能の仕様ではないので、**この文書が正本**。
`docs/elith/AI疾病予防報告書_仕様書.md` §4.6 はここを指すだけ。

---

## 1. 目的 — 何のためにダミーを見せるのか

| | |
|---|---|
| **UI デザインの確認** | 実データが無い段階でも画面の完成形を見る |
| **機能確認** | 推移グラフ（2 回目の検査から）・過去データの切替など、材料が要る機能を通す |
| **ビジネスパートナーへのお披露目・PR** | 商談・宣伝の場でサービスの実物を見せる |

**権限の確認ではない。** だから**権限の仕組み（admin）に乗せない。**
これが後述の「順序」の理由であり、この文書の中心。

---

## 2. 誰が見るか

| 閲覧者 | ダミー | 実データ |
|---|---|---|
| **デモ用アカウント**（uid が一覧にある） | **出す** | — |
| **admin の登録者** | **出す** | 出す |
| Google 認証済みの一般顧客 | **出さない** | **本人のぶんだけ** |
| 未サインイン | 出さない | 出さない |

**サインインは全員が通常どおり Google 認証を通る。**
デモ用アカウントは「素性の分かっている実在の Google アカウント」であって、**認証の抜け道ではない**。
認証をスキップする仕組み・共有パスワード・URL パラメータでの入場は**作らない**。

## 3. 判定 — 順序が要件そのもの

実装は `src/lib/demo-data.ts` の `demoFallbackEnabled(uid, viewerIsAdmin)`。**同期関数**。

```
① env PUBLIC_DEMO_FALLBACK === 'false' なら false   ← 唯一の全停止スイッチ
② uid が demoUids() にあれば true                    ← 本線
③ viewerIsAdmin なら true                            ← 追加
```

### なぜ ③ を ② より後ろに置くのか【最重要】

`viewerIsAdmin` は次の **3 段の外部依存**で決まる。

```
Cookie の署名 → HP Edge の resolve-customer → Wellfort 側 admin_users
```

**どこか 1 つが落ちても結果は同じ `false`** になり、**画面は黙って空になる**。
2026-08-30 に本番で `edge.is_admin: false` を実測しており、admin を入口にすると
**お披露目の当日に画面が空になる**。

② を先に評価すれば、**admin 判定が壊れていても登録済みのデモ用アカウントは確実に見られる**。
デモの成立が外部システムの状態に左右されない、というのがこの順序の意味。

> **③ を ② より前に戻さないこと。** `npm run verify:demo-gate` が順序を機械で見張っており、
> 戻すと落ちる（確認済み）。

### 代理表示（`?u=`）との関係

admin が `?u=<他人の uid>` で代理表示しているとき、ページは **`viewerIsAdmin` を渡さない**
（相手の実データを見せるため）。したがって ③ は使えない。
**それでも ② は効く** — ② は「表示中の uid」を見るので、**相手が登録済みならデモが出る**。

実測 2026-08-30: `?u=` 付きで `rp-h3`=3（`emptyVM`）→ 相手を登録して **45**（`?u=` なしと同一）。

## 4. デモ用アカウントの一覧 = 3 つの供給元の**和**

| 供給元 | 反映 | 用途 |
|---|---|---|
| `BUILTIN_DEMO_UIDS`（`demo-data.ts`） | 要デプロイ | **消えない下限**。ローンチ前の確認に必ず要るぶんだけ |
| env `DEMO_ALLOWED_UIDS`（カンマ/空白/改行 区切り） | 要デプロイ | DB 障害に影響されない |
| app_config `demo.account_uids` | **即時**（TTL 45 秒） | **admin から増減**。お披露目で当日足す |

### なぜ「上書き」でなく「和」か

上書きにすると、**admin で 1 件登録した瞬間に組み込みと env が消え**、
それまで見えていた画面が黙って空になる。**足せるが消せない**方が事故が軽い。

**全部止める手段は env `PUBLIC_DEMO_FALLBACK=false` だけ。** これが唯一の停止スイッチ。

### 組み込みを名簿として育てないこと

`BUILTIN_DEMO_UIDS` は「デプロイ無しでは消えない最小限」であって、名簿ではない。
ここに書き足す運用にすると、**アカウント 1 件ごとにデプロイが要る形に戻る**。
増えるぶんは app_config か env を使う。

**一般顧客の uid をここに書かない。** 常設になり、外すのに再デプロイが要る。

### 現在の組み込み（4 件・すべて実顧客ではない）

| uid | 何 |
|---|---|
| `d0000001-…` | テストフェーズの標準デモ（真鍋）。`supabase/seed.sql` の投入先・`DEFAULT_USER` |
| `da000001-…` | OEM 相手先ブランド向けデモ（山田太郎）。`supabase/demo_oem_account.sql` |
| `14410d5a-…` | 社内の確認用（2026-08-30 登録） |
| `186151f8-…` | 社内の確認用（2026-08-30 登録） |

後ろ 2 件を組み込みに置いたのは、**9/1 ローンチ前の確認に必ず要るので、
admin 判定や DB の状態に左右されない下限に置く**ため。

## 5. アカウントの増やし方

1. そのアカウントで Google サインインし、`/dashboard` の「デバッグ」で `diagnostic_user_id` をコピー
2. wellfort-site admin の Elith バッチ画面 → 設定モーダル →「**デモ**」→「**デモ用アカウントの uid**」に貼る

設定モーダルは `CONFIG_SPECS` から自動でグループ表示される（`elith-batch.astro:2071`）。
キーを 1 行足せば admin 画面に自動で出るので、**画面側の改修は要らない**。

**再デプロイ不要・反映は最大 45 秒。**

### 減らし方

app_config / env から外す。**組み込みの 4 件は外せない**（コード変更が要る）。
臨時に全部止めるなら `PUBLIC_DEMO_FALLBACK=false`。

## 6. 実装上の約束

| | |
|---|---|
| **同期関数のまま** | ~30 箇所から呼ばれる。async にすると全経路の書き換えになり、「DB が引けないと黙ってデモが消える」依存も増える |
| **`demoUids()` はキャッシュしない** | `cfg()` は TTL 45 秒で入れ替わる。固定すると admin の変更が反映されない |
| **`refreshConfig()` はデータ取得より前** | 後ろだと初回リクエストで admin の登録が効かず、コード既定に落ちる（5 ページとも） |
| **uid 未指定は false** | fail-safe をこちらへ倒す。誤ってダミーが出るより空表示の方が安全 |
| **admin 判定はデモの前提にしない** | ③ は追加条件。壊れてもデモは動く |

## 7. 検証 `npm run verify:demo-gate`

規則を**実装と独立に書き下して**突き合わせる（12 ケース）。`npm run verify:report` に同梱。

見ているもの:

- 12 ケースの真偽（デモ用アカウント / パートナー登録 / admin / 一般顧客 / 未サインイン × env）
- **評価順序**（①env → ②uid → ③admin）
- 供給元 3 つが**和**として生きていること・キャッシュしていないこと
- `app_config` にキーがあること・5 ページが `refreshConfig()` を先に呼ぶこと
- **admin 判定に名簿を持ち込んでいないこと**（ベタ書きが復活したら落とす）
- 「admin 判定が壊れてもデモ用アカウントは見られる」
- 「代理表示の相手がデモ用アカウントなら出る」

### ここは静かに壊れる

失敗の出方は 2 つで、**どちらも画面を見ただけでは気づけない**。

1. デモ用アカウントで画面が空になる → **お披露目の当日に気づく**
2. 実顧客に他人名義のダミーが「自分の結果」として出る → **気づかれないまま流出する**

だから規則を表で固定する。**実装を読んで期待値を書かない**（「実装が実装どおり」を確認するだけになる）。

## 8. 切り分け

```
GET https://scan-chat-ai.vercel.app/api/debug/viewer?k=<PROBE_UPLOAD_TOKEN>
```

| 出力 | 意味 |
|---|---|
| `report.demo_enabled: false` | デモが出ていない → uid を登録する |
| `report.effective_uid` | **画面が実際に使っている uid**（Cookie の uid とは限らない） |
| `viewer.is_admin` ≠ `edge.is_admin` | `warning` に出る。Cookie が古い＝期限切れで admin を失う |
| `edge.admin_lookup` | `readable` / `active_count` / `matched` で admin 照会の失敗と不在を区別 |

**`?u=` が付いていないか必ず確認する。** 代理表示中は相手の uid で判定されるので、
相手がデモ用アカウントでなければ空になる。**2026-08-30 にこれで 2 時間溶かした。**

`PROBE_UPLOAD_TOKEN` は使い捨ての運用トークン。**リポジトリに置かない**。
用が済んだら Vercel の env ごと削除してよい（削除すると診断は 503 になる）。
