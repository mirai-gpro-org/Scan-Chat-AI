## 0. サマリ (最初に読む)

- 対象は Web ポータル `dl.demecal.net` からの **汎用CSV ダウンロード**（動画・提供資料で確認済）。
- **認証はクライアント証明書 (相互TLS) ＋ ID/パスワード**。自動化は**この証明書を提示できること**が前提。
- 日付重複は「**前回取得済みの最終日を状態管理**し、次回開始日 = 前回終了日+1日」で回避する。
- **実装前に検査会社 (株式会社Leisure / Demecal) へ「自動アクセスの可否」を必ず確認**する (§6)。許諾なしに着手しない。
- 本アプローチ (ブラウザ/HTTP 自動化) 以外に、**公式データ連携 (API/SFTP/バッチ配信)** の選択肢がある (§7)。可能なら公式連携が最善。

### 運用確定 (2026-07 合意) ★
- §6 の**自動アクセスは承認済**。
- 実行環境は **専用デスクトップPC (Pマーク対応・個人用でない)**。デメカル証明書は**このPCのOS/ブラウザ証明書ストアに導入済**。
- 担当者は **admin を Google 認証** (Supabase Google OAuth) でログインして操作。
- 本命方式は **案2: Power Automate Desktop**（実ブラウザがOSストア証明書を使う）。Playwright(案A) は `.p12` を扱える場合の代替。
- **鍵は Vercel に一元管理・PCに置かない**を維持: PCは「DLのみ」、変換/S3/状態は Vercel(既存API)。
- **attended(担当者クリック)を先行**、無人(週次)は後段。認可は attended=Google短命トークン / unattended=取り込み専用キー `x-intake-key`(`LAB_INTAKE_API_KEY`)。
- 実装済: サーバ側(`elith-blood-csv` に `max_test_date`、状態API `demecal-state`、intake-key)・admin取り込みUI。
- **詳細な運用/実装設計は `demecal_rpa_operation_design.md` を参照**。

## 1. 背景・目的

血液検査 (デメカル) の結果は、検査会社のポータルから CSV でダウンロードして取得している。
現状は Wellfort スタッフが手作業で「ログイン → 日付範囲指定 → CSV ダウンロード」を実施 (要件2)。
これを **RPA/自動化し、日付が重複しないよう定期的に自動ダウンロード**する仕組みを構築するのが目的。

本自動化は要件2「検査結果の取り込み」の**手動工程の代替**であり、将来的な検査会社との
データ連携 (要件2 R2-6) への橋渡しでもある。

## 2. 現状の手動フロー (動画・提供資料より判明した事実)

### 2.1 操作手順 (汎用CSV)

1. 証明書導入済みの PC で Chrome を起動 → `https://dl.demecal.net/account/login`
2. **ログイン**: ユーザーID (代理店コード `Q05-0010`) ＋ パスワード
3. メニュー「データダウンロード」→「結果DL (汎用CSV)」 (別に「到着リスト」機能あり)
4. 「汎用CSVのダウンロード」画面
   - 代理店 `Q05-0010` / 販売先 `000000`
   - **日付範囲【必須】** from〜to (「出力日より前を指定」)
   - 検査結果: 正常終了のみ / 全部
   - 項目見出し: 出力する / しない
   - 画面下に**ダウンロード履歴** (過去の範囲・件数)
5. 「確認」→ 確認画面 → 「ダウンロード」
6. CSV 保存: ファイル名 `Q05-0010-000000result_{ダウンロード日 YYYYMMDD}_{件数}.csv`

### 2.2 認証方式 (最重要)

提供資料の「クライアント証明書インストール手順」に明記:

- Web システムは**各社専用のクライアント証明書 (相互TLS)** が必要。
  **証明書未導入の PC からはアクセス不可**。
- 必要ファイル: `demecal.net_CA.cer` (CA証明書) / `<代理店コード>.p12` (クライアント証明書) /
  ログイン用 ID・パスワード。
- 導入先: CA証明書=「信頼されたルート証明機関」、クライアント証明書=「個人」ストア。
- 動作確認環境: Chrome / Edge (最新) ＋ Windows 10 (macOS 非対応)。

> **含意**: 自動化プロセスも「証明書提示 ＋ ID/PW」を満たす必要がある。単純な URL 直叩きでは到達しない。

### 2.3 日付重複の課題

ダウンロード履歴上、範囲が手動指定のため**重複・隙間**が発生している (例: `2025/12/01〜2026/06/11` と
`2025/12/01〜2026/02/03` が重複)。自動化では状態管理で連続範囲を保証する (§4)。

## 3. 自動ダウンロードの方式 (本アプローチ)

### 3.1 方式候補

| 方式 | 証明書の与え方 | 特徴 |
|---|---|---|
| **A. ヘッドレス・ブラウザ自動化 (Playwright)** 〔推奨〕 | コードから `.p12` を提示 (`clientCertificates`) | 既存 TS/Node スタックと親和。画面操作を忠実に再現。状態管理・連携まで内製可 |
| B. HTTP クライアント直接 (client cert 付き) | HTTP レイヤで `.p12`/`pfx` を提示 | ブラウザ不要で軽量・高速。ただし画面遷移/トークン/POST パラメータの解析が必要 |
| C. デスクトップ RPA (Power Automate 等) を証明書導入済み PC で常駐 | OS/ブラウザ証明書ストア | 現行運用に近い。非エンジニアでも保守しやすい。PC 常駐が前提 |

推奨は **A (Playwright)**。理由: 認証(証明書)・画面遷移をそのまま扱え、後続の CSV 連携 (要件2/S3) を
同一コードベースで組める。B は最も軽いが保守が壊れやすい。C は現場運用向き。

### 3.2 自動化フロー (方式A/B 共通の論理)

```
[状態読込] 前回終了日 last_to を取得
   ↓
[認証]  dl.demecal.net にクライアント証明書を提示 → ID/PW でログイン
   ↓
[範囲決定] from = last_to + 1日 ,  to = 実行日 - 1日 (出力日より前)
   ↓
[取得]  汎用CSV: 日付範囲/検査結果/項目見出しを設定 → 確認 → ダウンロード
   ↓
[保存]  CSV を所定フォルダ/ストレージへ (命名規約は §5)
   ↓
[状態更新] last_to = to を保存 → 次回は重複なく継続
   ↓
[連携(任意)] 要件2 (/admin/lab-results/upload → test_artifacts) / S3 取り込みへ
```

## 4. 日付重複回避 (要望の核心)

- **状態管理**: 「前回取得済みの最終日 `last_to`」を永続化 (ファイル or DB)。
- **範囲決定**: 毎回 `from = last_to + 1日`、`to = 実行日 - 1日`。
- **原子性**: ダウンロード成功を確認してから `last_to` を更新 (失敗時は更新しない=次回リトライで欠損防止)。
- **注意**: ファイル名はダウンロード日ベースで**取得範囲を含まない**ため、重複判定はファイル名でなく
  **必ず状態 (`last_to`) で行う**。
- **境界**: 初回のみ開始日を手動指定 (例: 運用開始日 or 過去分の起点)。

---

## 5. 保存・命名・後続連携

- 取得 CSV は所定フォルダ/ストレージに保存。既存命名を踏襲: `Q05-0010-000000result_{YYYYMMDD}_{件数}.csv`。
- 追加で `range_{from}_{to}` を付すと範囲が識別でき運用が楽 (要検討)。
- **連携 (任意・推奨)**: 取得後に要件2 の取り込み (`test_artifacts` / `test_artifact_files`) へ渡し、
  さらに Elith 用 S3 (`BloodTestData`) へ繋げば、手作業を全廃できる。

## 6. 検査会社への確認事項 (実装前の必須ゲート) ★

自動アクセスは、利用規約・セキュリティ運用に触れる可能性があるため、**着手前に株式会社Leisure
(Demecal) へ可否を確認**する。以下を照会:

1. **自動 (プログラム/RPA) アクセスの可否** — 規約上・技術上、機械的ログイン＆ダウンロードは許容されるか。
2. **推奨手段の有無** — ポータル操作の代わりに**公式 API / SFTP / バッチ配信**等の提供はあるか (§7)。
3. **アクセス制限** — レート制限・同時接続・アクセス時間帯・IP 制限などの制約。
4. **クライアント証明書の扱い** — 自動化サーバへ証明書を導入して利用してよいか。有効期限・更新手順・
   複数端末利用の可否。
5. **認証情報の非対話利用** — ID/PW をスクリプトで用いることの可否 (MFA 等の有無)。
6. **連絡窓口・障害時の運用** — 仕様変更やメンテナンス時の通知経路。

> 許諾が得られない/条件が付く場合は、方式を §7 の公式連携に切替、または運用条件に合わせて設計を調整する。

## 7. 本アプローチ以外の方法 (代替案)

| 案 | 概要 | 長所 | 短所 |
|---|---|---|---|
| **① 公式データ連携 (API / SFTP / バッチ配信)** 〔理想〕 | 検査会社がCSV/データを API 提供 or SFTP/所定領域へ自動配信 | 最も堅牢・規約的にクリーン・画面変更に強い | 提供有無は先方次第。要調整・費用の可能性 |
| ② 結果の Push 配信 (メール/ストレージ) | 完了時に先方が CSV をメール/共有ストレージへ送付 | ポータル操作不要 | 先方対応が前提。取り込み側の自動処理が必要 |
| ③ HTTP直接呼び出し (証明書付き) | ブラウザを使わず HTTP で取得 (方式B) | 軽量・高速・サーバ常駐向き | 画面/トークン解析が必要、仕様変更に弱い |
| ④ ブラウザ自動化 (Playwright) 〔本命の実装〕 | 画面操作を忠実に自動化 (方式A) | 現行フローに忠実・内製しやすい | 画面変更で要メンテ・証明書運用が必要 |
| ⑤ デスクトップ RPA (証明書PCに常駐) | 現行 PC で自動操作 (方式C) | 現場運用に近い・導入容易 | PC 常駐依存・スケール性低 |

**推奨スタンス**:
1. まず **① 公式連携の有無を §6 で先方に確認**。あれば最優先で採用。
2. 無ければ **④ Playwright** を本命に、日付重複回避＋定期実行＋要件2/S3連携を内製。
3. 現場都合が強ければ ⑤ を暫定。

## 8. 認証情報・証明書のセキュリティ / 運用

- **秘密情報**: クライアント証明書 (`.p12`, 秘密鍵) ・ログイン ID/PW は機微情報。
  **リポジトリにコミットしない**。シークレット管理 (環境変数 / Vault / OS 証明書ストア) で保持。
- **実行環境**: 自動化サーバ (or 証明書導入済み専用端末) に限定。アクセスログを保全。
- **証明書更新**: 有効期限あり (CA は 2028 年まで、クライアント証明書は別途)。**失効/更新時は自動化も更新**が必要 →
  運用手順・監視に含める。
- **PII**: 取得 CSV は健康情報。保管・転送は要件群の PII 方針 (`data_integration_requirements.md`) に準拠。

## 9. 定期実行・監視

- **スケジュール: 週次** (Windows タスクスケジューラ / cron / CI)。実行曜日・時刻は運用で確定 (例: 毎週月曜 早朝)。
  - 1 回の実行で**直近約 1 週間分**を取得 (`from = last_to + 1日`、`to = 実行日 - 1日`、§4)。
  - 週次のため、祝日・障害でスキップしても次回に前回終了日から継続 → **取得漏れなく自動キャッチアップ**。
- 監視: 取得成功/失敗、取得件数、`last_to` の進捗を記録。失敗時アラート。
- 冪等性: 同一範囲の再実行でも重複しない (状態管理 §4)。

### 9.1 週次運用での留意点 (報告遅延)

- 「日付範囲」が**報告日 (登録日) 基準**なら、週次の非重複ウィンドウで漏れは生じない
  (今週報告分は今週のウィンドウに入る)。
- 一方で**検体採取日基準**の場合、検査結果が数日遅れて反映されると、既に取得済みの範囲に
  後から結果が追加され**取り漏れ**が起きうる。→ 「日付範囲が何日基準か」を先方に確認 (§6 / §10 #7)。
  - 対策案: ウィンドウ終端に**数日のマージン**を設ける (`to = 実行日 - N日`) か、直近数週間を
    定期的に**再取得して差分マージ** (件数/内容で重複排除)。基準確認後に方式決定。
