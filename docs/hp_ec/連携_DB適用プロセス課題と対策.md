# 【課題共有・要協議】#2(診断系) DB スキーマ適用プロセスの問題と対策案

- 作成: Web アプリ（Scan-Chat / マイページ）チーム
- 宛先: HP/EC（wellfort-site）チーム / #2 DB 権限者
- 日付: 2026-06-21
- 位置付け: **対症療法（個別 SQL の都度適用）をやめ、根本原因と運用プロセスを合意するための叩き台。**

---

## 1. 何が起きているか（現状の事実）

直近、マイページのお知らせ機能まわりで**段階的にエラーが連鎖**しました。

| # | 事象 | 示唆 |
|---|---|---|
| 1 | ダッシュボードは表示できる（`app_users`/`test_artifacts` 等を読めている） | アプリ接続先 DB には **diagnosis 基盤テーブルがある** |
| 2 | 「お知らせ」を開くと `diagnosis.user_notices` が無いエラー | その DB に **お知らせ系マイグレが未適用** |
| 3 | お知らせ SQL を実行したら `diagnosis.app_users does not exist` | SQL を当てた DB には **基盤テーブルすら無い**（＝事象1の DB と別物、または空の別プロジェクト） |

→ **「アプリが読む DB」と「マイグレ／SQL を当てている DB」が一致していない（あるいは複数の Supabase が歯抜け状態で混在している）**ことが露呈しました。

## 2. 根本原因（プロセス／構成の問題）

個別のテーブル欠落は**症状**で、原因は以下の構造的ギャップです。

- **A. #2 のスキーマ状態が台帳化されていない**
  どの Supabase プロジェクトが「正の #2」で、各プロジェクトに**どのマイグレまで適用済みか**の共有された記録が無い。だから新規テーブル（notices）も基盤も歯抜けになる。
- **B. マイグレ適用の責任分界・手順が未定義**
  マイグレは Web が作成、適用は権限者（HP/EC）側、という大枠はあるが、「**いつ・どの手順（`supabase db push`?）・どのプロジェクトへ**」が決まっていない。都度 SQL 手貼りになり、抜けや実行先ズレが起きる。
- **C. dev(単一結合) → 本番(2分離) のマイグレ構成が未整理**
  現行マイグレは `customer`＋`diagnosis` を**1プロジェクトに作る dev 前提**。#2（diagnosis 単独）へどう適用するか（`customer` スキーマを #2 に作るのか等）が未定義。
- **D. 環境変数（接続先）の単一の正が未確定**
  アプリ（Vercel 本番/プレビュー）の `PUBLIC_SUPABASE_URL`、SQL を当てる先、Edge Function が書く先が**同一の #2 を指している保証が無い**。

## 3. まず共有・確認したいこと（HP/EC へ）

対策を決める前に、現状を可視化したいです。

1. **#2 として稼働中の Supabase プロジェクトは何個あり、どれが「正」か**（dev 結合 / 本番 #2 / その他）。
2. **各プロジェクトの適用済みマイグレ**：
   ```sql
   select version, name from supabase_migrations.schema_migrations order by version;
   -- もしくは存在確認:
   select to_regclass('diagnosis.app_users'), to_regclass('diagnosis.user_notices');
   ```
3. **アプリ（Vercel 本番/プレビュー）の `PUBLIC_SUPABASE_URL` / `SERVICE_ROLE_KEY` が指す #2** はどれか。
4. **#2 へのマイグレ適用手段**：Supabase CLI で link 済みか（`supabase db push` 可能か）、それとも SQL Editor 手動のみか。
5. **#2 に `customer` スキーマを置く方針か**（dev フォールバック維持のため）／**`diagnosis` のみ**にするか。

## 4. 対策案（擦り合わせたい）

### 4-1. 即時（ブロッカー解消）
- **「アプリが実際に接続している #2」を1つ確定**し、その**同一 DB に不足マイグレを順序どおり一括適用**する。
  - 推奨: `supabase db push`（未適用ぶんを base→お知らせまで順に反映）。
  - 手動なら順序: `20260601000010` → `20260601000020` → `20260620000010` → `20260621000010` → `20260621000020`。
- 個別 SQL（`apply_notices.sql`）の単発適用は**やめる**（前提欠落で連鎖エラーになるため）。基盤から通しで入れる。

### 4-2. 恒久（運用プロセス化）
| 案 | 内容 | 長所 | 短所 |
|---|---|---|---|
| P1 | **#2 のマイグレ運用を CLI link + `db push` に一本化**し、`schema_migrations` で状態管理 | 歯抜け・実行先ズレを構造的に防止 | 初期 link 設定が必要 |
| P2 | **責任分界の明文化**: Web がマイグレ作成・PR → 権限者が #2 へ `db push`（定例 or PR マージ時） | 役割が明確 | 運用ルール合意が必要 |
| P3 | **Web に #2 の適用権限を限定付与**（マイグレ専用）し、Web 側でデプロイ時に適用 | リードタイム短縮 | 権限管理の検討 |
| P4 | **dev→本番のマイグレ構成整理**: #2 を `diagnosis` のみにするなら**diagnosis 専用マイグレ束を切り出す**／当面 dev 互換で `customer` も #2 に作る | 構成が明確に | 切り出し作業 |
| P5 | **環境変数の単一の正を確定**（アプリ・SQL適用・Edge Function が同一 #2 を指す）＋ CI で疎通チェック | 接続先ズレを根絶 | — |

**Web 側の推奨**: 短期=4-1 で正の #2 に通しで適用 → 解消。恒久=**P1＋P2＋P5** を基本線に、#2 のスキーマ範囲（P4）を §3-5 の回答で確定。

## 5. お願い
- §3 の1〜5にご回答ください（特に「正の #2 はどれ」「適用済みマイグレ」「アプリの接続先」）。
- そのうえで §4 の恒久案（P1/P2/P5 ＋ P4 の方針）を一緒に確定したいです。
- 以後は**個別 SQL の手貼りではなく、合意した適用プロセス**で流す形に切り替えましょう。

> 補足: Web 側のコード／マイグレ自体は揃っており `astro check`/`build` 通過済みです。本件は**コード不具合ではなく、#2 への適用プロセスと環境整合**の問題です。
