## 1. Mission / Vision

### Mission
> がんや生活習慣病を、**健康モニタリング**により早期発見および予防し、健康寿命を大幅に伸ばし、豊かな人生を実現する。

### Vision
> 病気になる前に予防をする。**健康投資**があたりまえの世の中に。

## 2. プロダクト哲学

### コンセプト: 「読ませるレポート」から「行動を促すダッシュボード」へ

従来の検査結果は紙またはテキスト中心の「レポート」であり、ユーザーが自力で読み解いて行動に繋げるハードルが極めて高かった。本プロダクトは LLM を駆使して、**検査結果 + 推移 + AI 診断所見**を統合し、ユーザーが「次の一歩」を踏み出せる**アクション・ダッシュボード**として再構成する。

### LLM を駆使する 3 つの局面

| 局面 | 役割 | パイロット状況 |
|---|---|---|
| **取込** | 検査票の解読・転記の自動化 (素人には難解な医療データの民主化) | 実装済 (撮影 + PDF/画像アップロード) |
| **問診** | 会話型 UX で生活習慣を網羅的に把握 | 実装済 (5 セクション、音声/テキスト・ハイブリッド) |
| **提示** | 重要度を AI が判定 → グラフ + 行動提案で「促す」 | Phase 1 で本格化 |

### 設計原則 (Perception と Reasoning の分離)

医療データ処理は「**紙面から正しい値を読む (Perception)**」と「**読み取った値の臨床的意味を解釈する (Reasoning)**」という二つの全く異なるタスクから成る。それぞれに適したモデル・サービスを充てる:

| レイヤ | 担当 | モデル |
|---|---|---|
| Perception | Scan-Chat-AI (本リポジトリ) | Gemini 2.5 Flash (転記) / Gemini 3.1 Flash Live (音声問診) |
| Reasoning | Elith AI 診断 | Gemma 4 / Qwen 3.5 等の医療特化 LLM |

詳細: `system_architecture_overview.md §1.1`

## 3. 戦略目標 (5 つの柱)

### 目標 1: 検査データの低摩擦・高精度取込

検査票は素人に難解で煩雑。ユーザーの手間を出来る限り廃した取込を、LLM (Gemini マルチモーダル) で実現する。

- ユーザー操作: **撮影 or ファイル選択のみ** で完結
- フォーマット非依存: 人間ドック・健診・血液検査・がん検査・遺伝子検査の各社フォーマットを zero-shot で処理
- 精度: 「読み取った値」と「AI 推論値」を分離し、**人間目視確認 UI** で監査
- **パイロット版実装済** (PDF / JPEG / PNG / WebP / HEIC 対応、最大 4 MB)

### 目標 2: Elith AI 診断システムへのスムーズ連携

- **同一 AWS アカウント内**、ただし**コンテナは分離** (関心の分離 + 再デプロイ独立性)
- 連携方式: **AWS S3 経由のバッチ連携** (非同期)
- ペイロード: Markdown ファースト (LLM ネイティブ形式、ベンダー間疎結合)
- 識別子: `diagnostic_id` (UUID) のみ。**PII は越境させない**

詳細: `data_integration_requirements.md`

### 目標 3: AI 問診による生活習慣の網羅把握

- パイロット版実装済 (5 セクション: 嗜好品 / 運動 / 食生活 / 睡眠 / 心身)
- 環境適応型: 自宅では音声 Live API、移動中はテキスト + 選択肢タップ
- 出力: `interrogation_md` (Markdown 形式) を Elith に渡す

### 目標 4: AI 診断結果の「行動を促す」配信

Elith から戻る診断結果報告書を起点に、LLM で再構成して **行動誘発型** に変換する。

- 「サマリ → 注目項目 → 具体的アクション」の 3 階構造
- ユーザーが「今日できる 1 アクション」を必ず提示
- 医学用語は平易な日本語に書き換え

### 目標 5: 検査データ推移の可視化

- **LLM が重要指標を判定** (例: 血糖値・血圧・体脂肪・HbA1c など)
- 過去複数回の検査データを**グラフ化**
- 数字の羅列ではなく、AI 診断の生活改善アドバイスと**並べて表示**
- "推移を見せる" 目的は「**行動を促す**」こと。閲覧の自己満足では終わらせない

## 4. 認証戦略

### Phase 1 (現行): Google One Tap が基本

| 項目 | 仕様 |
|---|---|
| プライマリ | **Google One Tap** (FedCM 対応、`signInWithIdToken`) |
| 救済策 | G アカウント未保有者向けに**メール認証** (マジックリンクまたは OTP) |
| 入場経路 | Wellfort HP マイページからのボタンリンク |
| **再認証ポリシー** | HP マイページから遷移しても、本アプリ側で **Google One Tap を再要求** (セッション継承しない) |
| 入場資格チェック | Wellfort EC で対象検査商品を購入済が前提 |

### Phase 2 (拡張): マイナ + JPKI 追加認証

| 項目 | 仕様 |
|---|---|
| 追加方式 | **マイナンバーカード + JPKI** (公的個人認証サービス) |
| 目的 | 医療データ取扱の**セキュリティと信頼性**を最大化、ユーザーの利便性向上 |
| UI 配置 | Phase 1 から **「マイナ + JPKI」追加認証ボタン** をグレーアウトで設置 (Phase 2 で活性化) |

詳細: `device_and_auth_requirements.md`

## 5. 入力検査データ — 3 つのソース

### a) ユーザー個別取込 (Web アプリ経由)

ユーザーが個人または会社で受けた検査結果を、本アプリで撮影またはアップロード:

| 種別 | フォーマット | 取込方法 |
|---|---|---|
| 人間ドック | **複数** (検査機関ごとに異なる) | カメラ / PDF / 画像 |
| 定期健康診断 | **複数** | カメラ / PDF / 画像 |
| その他検査 (血液検査等) | **複数** | カメラ / PDF / 画像 |

→ LLM マルチモーダル (Gemini 2.5 Flash) でフォーマット非依存に読み取り

### b) Wellfort 経由 (代理アップロード)

Wellfort 社側が個人別に自動または手動でアップロード:

| 種別 | フォーマット |
|---|---|
| 血液検査 | **固定** |
| 遺伝子検査 | **固定** |
| がんリスク検査 (尿) | **固定** |
| AI 疾病予測 (Elith 以外) | **固定** |

→ 固定フォーマットなので、将来 Document AI Custom Extractor に移行する候補 (Phase 2 以降)

### c) Elith AI への連携 (AWS S3 自動連携)

| 項目 | 内容 |
|---|---|
| 配置 | 同一 AWS アカウント、**コンテナは分離** |
| 連携方式 | **AWS S3 + バッチ** (非同期) |
| 入力 | a/b の取込データ (scan_md) + 問診結果 (interrogation_md) |
| 出力 | Elith AI 診断結果報告書 |
| 識別子 | `diagnostic_id` のみ (PII 非伝達) |

## 6. システム全体の構成

4 つの独立サービスから構成 (詳細: `system_architecture_overview.md §2`)

```
┌──────────────┐    ┌──────────────────────┐    ┌──────────────────┐
│ (a) HP / EC   │    │ (b) Scan-Chat-AI     │    │ (d) ユーザー Web   │
│  Wellfort     │    │  本リポジトリ           │    │  マイページ拡張     │
│  顧客マスタ・   │    │  取込・問診           │    │  結果ダッシュ      │
│  EC 購入       │    │  ステートレス         │    │  ボード            │
└───────┬──────┘    └───────────┬──────────┘    └──────────┬───────┘
        │                       │                          ▲
        └──── diagnostic_id ────┴── scan_md / ──┐          │
                                  interrogation_md          │
                                                ▼          │
                          ┌──────────────────────────────────┐
                          │ 診断系 DB (Supabase #2)            │
                          │ PII なし・diagnostic_id で識別      │
                          └──────────────────────────────────┘
                                                │
                                                ▼
                          ┌──────────────────────────────────┐
                          │ (c) 診断 AI (Elith)                │
                          │ AWS S3 連携 / バッチ              │
                          │ Phase 2 でクライアント AWS に移植   │
                          └──────────────────────────────────┘
```

設計上のキー原則:

1. **役割分業** — Perception (本リポジトリ) と Reasoning (Elith) を物理分離
2. **PII と医療データの物理分離** — 顧客系 DB と診断系 DB を 2 つに分け、`diagnostic_id` でのみ橋渡し
3. **Markdown ファースト** — AI 間通信は Markdown を一次形式とし、JSON 強制を最小化
4. **段階的構築** — Pilot → Supabase → AWS の 3 段で API 契約を不変に保つ

## 7. パイロット → 本番への進化ロードマップ

### Phase 0: パイロット (現在 — 本リポジトリ)
- ✓ 検査スキャン (撮影 + PDF/画像アップロード)
- ✓ AI 問診 (5 セクション、音声/テキスト・ハイブリッド)
- ✓ 結果のローカル端末ダウンロード (永続化なし)
- **目的**: AI 認識精度と UX の検証、クライアントへのプレゼンテーション

### Phase 1: 本番運用基盤
- Supabase 2 分割 (顧客系 + 診断系)
- Edge Function による Elith 連携
- Google One Tap + 入場資格チェック
- マイページ拡張: **行動を促すダッシュボード**
- 検査データ推移のグラフ化
- **目的**: 本格運用と AI 診断のループ確立

### Phase 2: スケーラビリティ + コンプライアンス
- AWS 完全移行 (RDS + Aurora + S3 + Bedrock/SageMaker)
- マイナ + JPKI 追加認証 (グレーアウトを活性化)
- Document AI Custom Extractor の段階導入 (固定フォーマットから)
- 推移ダッシュボードの本格化 (経時推移 × LLM アドバイス統合)
- **目的**: エンタープライズ SLA・スケーラビリティ・コンプライアンス達成
